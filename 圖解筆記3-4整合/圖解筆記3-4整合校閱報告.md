## 二、內容正確性驗證

### ✅ 正確無誤的項目

#### Go 語法正確性（語法卡 / 範例）
- `if err := run(); err != nil { return err }` — 正確的 if 短宣告語法
- `for _, r := range text { fmt.Println(r) }` — 正確，range string 取 rune
- `var _ io.Reader = (*bytes.Buffer)(nil)` — 正確的 compile-time interface 實作驗證慣用法
- `defer tx.Rollback()` 在 `tx.Commit()` 之前 — 正確的 transaction pattern（commit 成功後 Rollback 是 no-op）
- `db.SetMaxOpenConns(25)` / `SetMaxIdleConns(10)` / `SetConnMaxLifetime(30 * time.Minute)` — 正確的 connection pool 設定

#### database/sql 正確性
```go
// 正確：sql.Open 不代表連線建立，PingContext 才是真正驗證
db, err := sql.Open("pgx", dsn)
pingCtx, cancel := context.WithTimeout(ctx, 3*time.Second)
defer cancel()
err = db.PingContext(pingCtx)
```
這個說明**非常重要且正確**，是很多工程師的誤區。

#### Go 1.22 ServeMux 正確性
```go
mux.HandleFunc("GET /jobs/{id}", func(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id")
})
```
✅ 正確：`r.PathValue("id")` 是 Go 1.22 的新 API，語法正確。

#### slices / maps 正確性
```go
items := slices.Clone(input)
slices.Sort(items)
items = slices.Compact(items)
```
✅ 正確：`slices.Clone`、`slices.Sort`、`slices.Compact` 均為 Go 1.21 的標準函式，API 正確。

```go

maps.DeleteFunc(copy, func(k, v string) bool { return v == "" })
```

✅ 正確：`maps.Clone`、`maps.DeleteFunc` 均為 Go 1.21 API，語法正確。

#### OpenTelemetry 正確性

✅ 正確：OTel Go SDK 的標準 span 建立模式。

#### Prometheus 正確性

✅ 正確：`prometheus.NewCounterVec` 與 `MustRegister` 是標準用法。

#### Bounded Queue + Backpressure 正確性

### ⚠️ 需要注意的細節

#### 1. `maps.Keys` / `maps.Values` 標記為 Go 1.21 API — 實際需確認
```
["maps", [["Clone",...], ["Equal",...], ["DeleteFunc",...], ["Keys/Values",...]]]
```
> **說明**：`maps.Keys` 和 `maps.Values` 在 Go 1.21 標準庫中**不存在**，它們在 `golang.org/x/exp/maps` 實驗庫中。Go 1.23 才透過 `iter` 提供類似功能（`maps.Keys` 返回 `iter.Seq[K]`）。整合版中這個條目的標記可能造成誤解。
>
> **建議修正**：將 `Keys/Values` 改標示為「Go 1.23 `iter` / `x/exp/maps`」或移除，避免工程師在 Go 1.21 環境找不到這個 API。

#### 2. `slices.BinarySearch` 的回傳值語意
```
["slices", [["BinarySearch", "已排序 slice 搜尋"]]]
```
> **說明**：`slices.BinarySearch[S ~[]E, E cmp.Ordered](x S, target E) (int, bool)` 回傳 `(index int, found bool)`。當 `found == false` 時，`index` 是**插入位置**，不代表找到目標。筆記中描述為「已排序 slice 搜尋」是正確的，但使用時需留意 `found` 布林值，否則容易誤用 index。
>
> **建議**：在說明中補一句「回傳 `(index, found)`，`found=false` 時 index 為插入點。」

#### 3. 200 個語法例的程式碼內容高度共用
```javascript
code: snippets[category]  // 所有同分類的例子共用同一段 code
```
> **說明**：200 個語法例都用 `snippets[category]` 產生，同分類的 20-30 個案例程式碼完全相同，僅標題不同（如「宣告與型別 範例 1」到「宣告與型別 範例 20」）。這讓 200 個案例在實質上只有 10 個不同的 code snippet。
>
> **影響**：降低了語法例的查閱價值，讀者無法從中得到「200 種不同用法」。
>
> **建議**：這是當前版本最大的內容深度缺口，可在下一版為每個 title 補上獨立的短 snippet。

#### 4. Production Walkthrough 中的 TxOptions 細節
```go
tx, err := db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelReadCommitted})
```
> **說明**：這個寫法在 Go 的 `database/sql` 中是正確的。`sql.LevelReadCommitted` 是合法的隔離等級常數。✅ 正確，無需修改。補充說明：若使用 `pgx` 驅動，`LevelReadCommitted` 會被正確映射到 PostgreSQL 的 `READ COMMITTED`。
