## 3. Configuration

新增的 Prometheus config 重點：

| 項目 | 值 | 目的 |
|---|---|---|
| `scrape_interval` | `15s` | 教學用固定 scrape 間隔 |
| `evaluation_interval` | `15s` | 教學用固定 rule evaluation 間隔 |
| `rule_files` | `/etc/prometheus/rules/production-api-worker-alerts.yml` | 載入既有 alert rules |

| `metrics_path` | `/metrics` | 對應 production-api-worker metrics endpoint |

| 項目 | 內容 |

## 5. Troubleshooting

| 事項 | 結論 |
|---|---|
| API key 與 Prometheus scrape | 文件已標註正式環境需 bearer token file 或平台 secret |
| 本地 monitoring profile 範圍 | `monitoring` profile 是教學用，不宣稱正式監控已部署 |
| OpenAPI 與 runtime 行為 | OpenAPI 是合約 artifact，不取代 Go contract tests |
| Docker 可用性 | 靜態 checks 不依賴 Docker；runtime profile 留待 Docker 環境驗證 |

## 6. Best Practices

1. Alert rules 與 Prometheus config 要一起發版，避免 rules 檔存在但未被載入。
2. `API_KEY` 不應硬寫進 Prometheus config；正式環境用 secret mount 或平台 scrape auth。
3. API contract 需維持 Markdown、OpenAPI 與 Go contract tests 三者一致。
4. 後續若加入 Alertmanager、Grafana 或 SDK 生成，應延伸同一個 gate，而不是新增孤立文件。
