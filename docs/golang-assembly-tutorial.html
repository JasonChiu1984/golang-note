Overview

Assembly 不是架構設計工具，而是最後一哩的 CPU hot path 最佳化。先用 pure Go 寫對，再用 profile 證明慢點，最後才替換成 assembly。

適合

固定演算法核心

Checksum、hash-like scoring、encoding inner loop、SIMD-friendly loop。輸入輸出應是簡單 scalar、slice、pointer 與 length。

不適合

業務與 I/O

HTTP、JSON、DB、queue、OPC UA、Modbus、BACnet、PLC polling 都不應放進 assembly。這些瓶頸多在 I/O wait 與 timeout。

必要條件

可回退

每個 assembly function 都要有 pure Go fallback 與同一組測試資料，否則跨平台部署與 rollback 風險太高。

Architecture

Assembly 應該被包在最小 compute package 內。外層服務只依賴 Go 函式，不知道內部使用 `.s` 或 fallback。

架構重點：把 CPU architecture 差異限制在 `internal/compute`，不要讓外部 API、資料格式或部署流程依賴 assembly。

Setup

先建立最小 compute package。這裡不建立 HTTP server，讓 Assembly 教程保持單一關注點。

Configuration

Assembly 主要靠 build tags 和 GOARCH 控制，不建議用 runtime flag 直接切換未驗證路徑。

Build tags

平台檔案分工

  • score_amd64.go：宣告 assembly symbol。
  • score_amd64.s：amd64 實作。
  • score_generic.go：非 amd64 fallback。
  • score_test.go：所有平台共用驗證。
部署注意

若 production 會跑在 amd64 與 arm64 混合環境，必須在 CI 加入 GOARCH=amd64 與 GOARCH=arm64 的 build/test gate。

Example

範例實作 Score([]uint64) uint64。Go API 負責空值處理，內部 hot path 由平台實作決定。

internal/compute/score.go
package compute

func Score(values []uint64) uint64 {
	if len(values) == 0 {
		return 0
	}
	return score(values)
}
internal/compute/score_amd64.go
//go:build amd64

package compute

func score(values []uint64) uint64
internal/compute/score_generic.go
//go:build !amd64

package compute

func score(values []uint64) uint64 {
	var total uint64
	for _, value := range values {
		total += value
	}
	return total
}
internal/compute/score_amd64.s
//go:build amd64

#include "textflag.h"

// func score(values []uint64) uint64
TEXT ·score(SB), NOSPLIT, $0-32
	MOVQ values_base+0(FP), SI
	MOVQ values_len+8(FP), CX
	XORQ AX, AX

loop:
	TESTQ CX, CX
	JEQ done
	ADDQ (SI), AX
	ADDQ $8, SI
	DECQ CX
	JMP loop

done:
	MOVQ AX, ret+24(FP)
	RET
internal/compute/score_test.go
package compute

import "testing"

func TestScore(t *testing.T) {
	cases := []struct {
		name   string
		values []uint64
		want   uint64
	}{
		{name: "empty", values: nil, want: 0},
		{name: "small", values: []uint64{1, 2, 3, 4, 5}, want: 15},
		{name: "overflow", values: []uint64{^uint64(0), 1}, want: 0},
	}
	for _, tc := range cases {
		t.Run(tc.name, func(t *testing.T) {
			if got := Score(tc.values); got != tc.want {
				t.Fatalf("Score()=%d want %d", got, tc.want)
			}
		})
	}
}

func BenchmarkScore(b *testing.B) {
	values := make([]uint64, 4096)
	for i := range values {
		values[i] = uint64(i + 1)
	}
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		_ = Score(values)
	}
}

Verification

驗證要證明三件事：結果正確、目標平台可編譯、效能收益大於維護成本。

驗證項指令通過條件
功能測試go test ./... -count=1table tests 全部通過。
amd64 buildGOARCH=amd64 go test ./... -count=1assembly symbol 正確連結。
fallback buildGOARCH=arm64 go test ./... -count=1generic fallback 可用。
benchmarkgo test ./internal/compute -bench=. -benchmem -count=10記錄 ns/op、B/op、allocs/op 與 CPU/Go version。
反組譯go test -c ./internal/compute && go tool objdump -s 'score' compute.test能看到目標 symbol 與預期指令。
固定驗證指令
go test ./... -count=1
GOARCH=amd64 go test ./... -count=1
GOARCH=arm64 go test ./... -count=1
go test ./internal/compute -bench=. -benchmem -count=10
go test -c ./internal/compute
go tool objdump -s 'score' compute.test | sed -n '1,120p'

Troubleshooting

Go assembly 常見錯誤多半不是語法，而是 symbol、ABI、build tag、offset 或平台假設。

症狀可能原因處理方式
missing function bodyGo declaration 找不到 `.s` 實作。確認 score_amd64.go 和 score_amd64.s build tag 一致。
relocation target not definedsymbol 名稱不一致。同 package 使用 TEXT ·score(SB)，注意 middle dot。
結果錯誤但不 panicslice header offset 或 return offset 錯誤。用空值、小值、溢位與大資料 table tests 固定行為。
非 amd64 失敗fallback 缺失或 build constraint 錯。保留 score_generic.go 並跑 GOARCH=arm64 go test。
效能沒提升瓶頸不在該 loop，或 Go compiler 已足夠最佳化。用 pprof 與 benchstat 判斷，不要只看單次 benchmark。

Best Practices

Assembly 的價值在可測、可替換、可回退。任何不符合這三點的最佳化都應先停下來。

Do
  • 先寫 pure Go reference implementation。
  • 把 assembly 限制在 internal package。
  • 用固定 benchmark 和 raw output 記錄收益。
  • 每個 GOARCH 都有 build/test gate。
  • 在 release note 標註 Go version、GOARCH、CPU 與 benchmark 條件。
Avoid
  • 在 assembly 中處理 JSON、HTTP、DB 或 queue。
  • 沒有 fallback 就部署到多架構環境。
  • 只用單次 benchmark 宣稱效能提升。
  • 讓外部 API 曝露 CPU architecture 差異。
  • 為了展示技術而導入 assembly。
