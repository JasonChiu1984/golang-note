分類地圖

第三方模組不要一次全裝。先按 bounded context 選出必要能力，再用測試、依賴掃描與安全檢查驗收。

Web / API

Router、middleware、RPC

適合 REST、內部 API、gateway、microservice 通訊。

Database

SQL、ORM、migration

以 `database/sql`、pgx、migration、transaction boundary 為核心。

Config / CLI

設定、命令列、環境變數

讓服務啟動設定可驗證、可覆寫、可文件化。

Observability

log、metrics、trace

production service 必須能對照 request id、error code 與 trace。

Testing

assert、mock、container test

固定 API contract、資料庫整合、併發與錯誤路徑。

Security

JWT、RBAC、crypto helper

導入前要先定義 threat model，不以套件存在取代安全設計。

選型流程

用工程證據選 module，而不是只看 star 數或網路範例。

模組清單

可用分類按鈕與搜尋框快速篩選。建議先從「標準庫能否滿足」開始判斷，再導入第三方 module。

導入驗證指令

每次新增第三方模組都應留下可重複驗證紀錄。

目的指令驗收重點
整理依賴go mod tidy`go.mod` / `go.sum` 只留下實際需要的 module。
校驗 module hashgo mod verify確認 module cache 未被竄改。
列出可更新版本go list -m -u all知道導入時是否已落後 major/minor/patch。
漏洞掃描govulncheck ./...檢查可達漏洞，不只看 dependency tree。
全量測試go test ./... -count=1避免新依賴破壞既有 package。
Race testgo test -race ./...對 cache、worker、HTTP middleware、DB pool 特別重要。
API contractgo test ./internal/api -run 'Test.*Contract' -count=1第三方 router / encoder / validator 不應改變外部 schema。
效能基線go test -run='^$' -bench=. -benchmem ./...替換 logger、router、serializer、DB driver 前後要有 benchmark。

風險註記

第三方 module 是工程資產，也是維護負債。

導入前

  • 確認標準庫是否已足夠，例如 `net/http`、`database/sql`、`log/slog`、`flag`。
  • 確認 module 是否有 tagged version、license、活躍維護、Go version policy。
  • 評估 API 是否會滲透到 domain layer，避免未來替換成本過高。

導入後

  • 把初始化與 adapter 放在邊界層，domain / application layer 不直接綁死套件型別。
  • 把設定、timeout、retry、logger、metrics label 寫成合約與測試。
  • 每次升級保留 changelog、test result、rollback plan。

來源與更新方式

清單以 `pkg.go.dev`、各專案文件與 Go 官方依賴治理流程為基準。實際導入前仍需重新確認版本、license、Go support policy 與 CVE 狀態。

go env GOPROXY
go list -m -versions <module>
go list -m -u all
