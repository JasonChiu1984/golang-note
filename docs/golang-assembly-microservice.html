Overview

Go assembly 不應變成微服務主要設計語言。正確定位是：只優化可量測、可隔離、可回退的 CPU hot path。

適合

固定演算法核心

Checksum、hash-like scoring、SIMD-friendly loop、encoding/decoding inner loop。輸入輸出型別要簡單，避免在 assembly 內處理複雜 Go object。

不適合

業務流程與 I/O

HTTP、資料庫、message queue、PLC polling、OPC UA / Modbus 通訊都應留在 Go。I/O-bound 場景通常不該先寫 assembly。

必要條件

benchmark 先行

沒有 `go test -bench`、pprof 或 production metrics 證據，就不應導入 assembly。每個 assembly path 都要有 pure Go fallback。

Architecture

微服務仍以 Go 標準庫建立邊界，assembly 僅透過小型 adapter 暴露一個可測函式。

架構重點：assembly function 是 service 內部 implementation detail，不應直接暴露成外部 API 合約。

Setup

以下範例使用標準庫，不需要 Gin、Fiber 或外部依賴。目標是讓 assembly 邊界清楚、可測、可替換。

需求建議原因
Go toolchain`go version` 確認本機版本assembly 與 ABI 細節會受 Go 版本與 GOARCH 影響，release 前需固定版本。
目標平台先做 `amd64`，再決定是否支援 `arm64`Go assembly 是架構相關；不要假設 `.s` 可跨 CPU 重用。
fallback每個 assembly function 都有 pure Go 版本支援非目標平台、測試 oracle 與快速 rollback。
benchmark`go test -bench=. -benchmem -count=10`沒有前後數據就不能判斷 assembly 是否值得維護成本。

Configuration

設定不要寫死在 handler。即使是 assembly demo，也應維持 production 微服務的 timeout 與 engine selection 邊界。

Env

服務設定

  • `PORT=8080`：HTTP listen port。
  • `REQUEST_TIMEOUT=2s`：單次計算 API 的 request timeout。
  • `ENGINE=auto|asm|go`：選擇 assembly、pure Go 或自動偵測。
風險提醒

不要讓外部 request 自由切換任意 assembly function。engine selection 應是部署設定，不是公開 API 參數，避免測試或攻擊流量觸發未驗證路徑。

Example

範例 API：`POST /score` 接收 `values`，回傳整數 score。assembly 僅負責加總 `[]uint64`，HTTP、JSON、timeout 都留在 Go。

internal/compute/score.go
package compute

func Score(values []uint64) uint64 {
	if len(values) == 0 {
		return 0
	}
	return score(values)
}

internal/api/handler.go
package api

import (
	"context"
	"encoding/json"
	"net/http"
	"time"

	"example.com/go-asm-service/internal/compute"
)

type ScoreRequest struct {
	Values []uint64 `json:"values"`
}

type ScoreResponse struct {
	Score uint64 `json:"score"`
}

func NewHandler(timeout time.Duration) http.Handler {
	mux := http.NewServeMux()
	mux.HandleFunc("POST /score", func(w http.ResponseWriter, r *http.Request) {
		ctx, cancel := context.WithTimeout(r.Context(), timeout)
		defer cancel()

		var input ScoreRequest
		if err := json.NewDecoder(r.Body).Decode(&input); err != nil {
			http.Error(w, "invalid json", http.StatusBadRequest)
			return
		}
		select {
		case <-ctx.Done():
			http.Error(w, "request timeout", http.StatusGatewayTimeout)
			return
		default:
		}

		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(ScoreResponse{Score: compute.Score(input.Values)})
	})
	return mux
}
cmd/server/main.go
package main

import (
	"log"
	"net/http"
	"os"
	"time"

	"example.com/go-asm-service/internal/api"
)

func main() {
	port := os.Getenv("PORT")
	if port == "" {
		port = "8080"
	}
	server := &http.Server{
		Addr:              ":" + port,
		Handler:           api.NewHandler(2 * time.Second),
		ReadHeaderTimeout: 3 * time.Second,
	}
	log.Printf("listening on :%s", port)
	log.Fatal(server.ListenAndServe())
}

Verification

驗證要同時確認功能正確、assembly 確實被編譯、效能值得維護，以及 fallback 可用。

驗證項指令通過條件
Unit test`go test ./... -count=1`API、compute、fallback tests 全部通過。
Race detector`go test -race ./...`HTTP handler 與 service 狀態沒有 data race。
Benchmark`go test ./internal/compute -bench=. -benchmem -count=10`比較 assembly 與 pure Go；記錄 CPU、Go version、GOARCH。
Disassembly`go tool objdump -s 'score' ./bin/server`可看到目標 symbol，並確認 release build 確實包含 assembly path。
Smoke test`curl -X POST /score`回傳 `{"score":15}` 這類穩定 JSON。
驗證注意

如果 benchmark 只快 1% 到 3%，通常不值得導入 assembly，因為維護成本、跨平台成本與 onboarding 成本會高於收益。

Troubleshooting

Go assembly 常見錯誤多半不是語法本身，而是 symbol、ABI、build tag、stack frame 或平台假設錯誤。

症狀可能原因處理方式
`missing function body`Go declaration 找不到對應 `.s` 實作，或 build tag 沒套上。確認 `score_amd64.go` 與 `score_amd64.s` 都有 `//go:build amd64`。
`relocation target not defined`symbol 名稱不一致。同 package 內使用 `TEXT ·score(SB)`，注意中間是 middle dot。
結果錯誤但不 panicslice header offset、return offset 或 register 使用錯誤。先用小輸入建立 table tests，再加 fuzz / property tests。
非 amd64 build 失敗沒有 fallback 或 build constraint 錯誤。保留 `score_generic.go`，並用 `GOARCH=arm64 go test ./...` 檢查 fallback。
效能沒有變快瓶頸不在該 loop，或 Go compiler 已足夠最佳化。用 pprof 找真正 hot path；不要憑直覺保留 assembly。

Best Practices

把 assembly 當作可替換的低階優化，不要讓它污染微服務架構。

Do
  • 先用 pure Go 寫出正確版本與測試。
  • 用 benchmark / pprof 證明 hot path。
  • assembly function 接受簡單型別，例如 slice、pointer、length。
  • 把 build tags、GOARCH、Go version 寫進 release note。
  • 保留 fallback，讓 rollback 不需要重寫服務。
Avoid
  • 在 assembly 內做 JSON、HTTP、DB 或 queue 邏輯。
  • 為了展示技術而導入 assembly。
  • 讓外部 API 依賴 CPU architecture。
  • 沒有 benchmark 就宣稱效能提升。
  • 沒有 fallback 就把服務部署到多架構環境。
