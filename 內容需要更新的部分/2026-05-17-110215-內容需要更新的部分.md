## 1. Overview

依審查報告，本輪更新目標是把 `production-api-worker` 的 observability 從「程式接線與概念」提升為「可值班、可告警、可驗證」的 operational runbook。

## 2. Architecture

| 更新項目 | 檔案 | 目的 |
|---|---|---|
| 新增 operational runbook | `production-api-worker/docs/operational-runbook.md` | 固定 SLI/SLO、incident workflow、verification、troubleshooting、risk notes |
| 新增 Prometheus alert rules | `configs/prometheus/production-api-worker-alerts.yml` | 提供 5xx、queue depth、worker latency、metrics missing 告警範例 |
| 新增 runbook 檢查腳本 | `scripts/check-operational-runbook.mjs` | 確認 runbook、alert rules、README 與 CI gate 都存在 |

## 3. Setup

需要新增或更新下列入口：

| 入口 | 更新內容 |
|---|---|
| `README.md` | 版本、更新重點、版本策略與驗證指令 |
| `production-api-worker/README.md` | release gate、CI workflow、performance diagnostics 與 operational runbook section |
| `.github/workflows/ci.yml` | root job 增加 runbook check |
| `production-api-worker/Makefile` | 增加 `runbook-check` target |

## 4. Configuration

Prometheus rule 需至少包含：

1. `ProductionAPIWorkerHigh5xxRate`
2. `ProductionAPIWorkerCritical5xxRate`
3. `ProductionAPIWorkerQueueDepthHigh`
4. `ProductionAPIWorkerWorkerLatencyHigh`
5. `ProductionAPIWorkerMetricsMissing`

每條 rule 需要 `severity`、`summary`、`description`、`runbook_url`。

## 5. Example

Runbook 需包含三個最小 incident flow：

| Flow | 內容 |
|---|---|
| API 5xx error rate 升高 | route / status 分析、request id correlation、contract test |
| Worker queue depth 偏高 | worker latency、DB pool、CPU throttling、benchmark |
| Readiness 失敗 | draining、container logs、compose smoke |

## 7. Troubleshooting

| 可能問題 | 處理方式 |
|---|---|
| `/metrics` 啟用 API key 後 scrape 失敗 | runbook 必須提醒 Prometheus scrape auth |
| alert threshold 被誤解為正式 SLA | runbook 必須標註教學 baseline 與正式環境需重算 |
| CI 無法執行 Docker | 本輪 runbook check 不依賴 Docker；Compose smoke 仍保留為部署 gate |

## 8. Best Practices

1. Runbook 與 alert rules 應與程式碼同 repo 管理。
2. Alert rule 必須連回可操作 runbook。
3. README 只放入口與驗證指令，細節放 runbook。
4. 每次 docs/index.html 重產後都跑 link fix。
