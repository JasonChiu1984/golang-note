## 結論

本教程針對 Go 專案開發的深度與廣度已符合進階工程教材水準。v1.0.73 已把 Prometheus scrape config、alert rules、Compose monitoring profile 與 API key scrape auth 風險納入正式 Prometheus config contract gate，代表 observability 已從概念、程式碼與 runbook 進一步走到可驗證的 release gate。

目前主要缺口不是新增 runtime feature，而是 trace pipeline 的 production export governance 還停留在文件提醒層級。`production-api-worker/otel-collector.yaml`、Compose endpoint 與 `scripts/check-otel-collector-contract.mjs` 已固定 local OTLP receiver / debug exporter，但正式環境替換 Tempo、Jaeger、OTLP backend 或雲端 APM 時，取樣率、資料保留、敏感欄位與 exporter 替換邊界尚未進入獨立 root contract checker inventory。

## 內部缺失

1. OTLP collector 目前固定 local receiver / debug exporter，但 production exporter governance 尚未成為獨立 gate。
   - 現況：`scripts/check-otel-collector-contract.mjs` 已檢查 collector config、Compose endpoint、runbook、README 與 CI。
   - 風險：正式環境替換 exporter 時，可能只保留 receiver wiring，卻沒有要求取樣率、資料保留、敏感欄位與 backend ownership 說明。
   - 影響：trace pipeline 可在 local mode 通過，但 production APM 接入策略無法被 release artifact chain 穩定追蹤。

2. runbook 已提到取樣策略與保存期限，但缺少 machine-checkable contract wording。
   - 現況：operational runbook 已列出「Trace backend 未固定」風險與 trace pipeline 可替換原則。
   - 風險：文件重整時可能移除 Tempo / Jaeger / OTLP backend、sampling rate、retention window 或 sensitive attribute redaction 的治理條款。
   - 影響：教材讀者容易把 local `debug exporter` 誤當成 production tracing architecture。

3. v1.0.73 後 inventory 基準仍停在 42。
   - 現況：root `scripts/check-*-contract.mjs` 共 42 個，版本與 artifact-chain 都以 v1.0.73 / 42 為基準。
   - 風險：若新增 OTLP production export governance checker 時只補文件，不同步 inventory script、release artifact chain、Makefile、CI 與 docs/index，會造成 release gate 漂移。
