## 三、主要缺失

### P1：Request timeout 尚未形成 HTTP contract

`production-api-worker/internal/app.Service` 已能在 deadlock retry backoff 期間尊重 `ctx.Done()`，但 API handler 的錯誤分類仍有缺口：當 request-scoped context 因 deadline exceeded 失敗時，`Handler.writeError` 會落到預設 `500 internal_error`。

這對 production service 會造成三個問題：

| 問題 | 影響 |
|---|---|
| timeout 被誤分類成 500 | client 無法分辨 timeout、未知 server bug 與 panic |
| error code 不穩定 | dashboard、alert、retry policy 只能依模糊訊息或 HTTP 500 判斷 |
| 教程語意不完整 | 第 7 / 11 章已談 context cancellation，但 HTTP 邊界尚未教如何分類 deadline |

### P2：API contract 文件缺少 `request_timeout`

`production-api-worker/docs/api-contract.md` 已固定 `invalid_input`、`not_found`、`queue_full`、`internal_error`，但缺少 timeout 分支。這會讓使用端和學習者誤以為 timeout 不需要合約，或可以被歸為一般 500。

### P3：教材矩陣尚未列出 timeout gate

README、第 7 章、第 11 章、進階 Cheat Sheet 與康乃爾筆記已有 request decoding、readiness、panic recovery、retry cancellation 等 gate，但缺少 `TestRequestTimeoutContract` 這種 focused test，導致 release 前不容易發現 timeout 分類漂移。

## 五、風險說明

- `context.Canceled` 常見於 client disconnect 或 shutdown cancellation，本輪先固定 `context.DeadlineExceeded`，避免引入非標準 HTTP 499 或混淆 408 的語意。
- `internal/api` 測試依賴 OpenTelemetry / Prometheus module；若離線或 DNS 受限，測試會卡在 module download，不能把失敗誤判為程式邏輯錯。
- 本機 toolchain 仍可能不是 Go 1.26.3；Go 1.26 新功能內容屬教材基準，實際執行需用對應 toolchain 驗證。
