## 1. Overview

`Golang學習筆記` 已從語法教材演進到可執行 production 範例。`production-api-worker` 目前具備 API contract、OpenAPI、API key security、migration、DB pool、request timeout、panic recovery、queue shutdown、Prometheus config、operational runbook 與 Compose smoke gate。

本輪審查結論：教材深度已符合「可帶新人進入專案開發」的要求，但 production diagnostics 仍缺一個關鍵安全層。教材多處提到 pprof 與 production debug，卻尚未把 `/debug/pprof/` 的啟用條件、認證邊界、測試與 runbook gate 轉成可執行合約。這會讓學習者誤以為只要 `import _ "net/http/pprof"` 就能直接上 production，安全假設不足。

## 3. Workflow 審查

目前 workflow 已能從文件走到驗證：

1. `README.md` 定義版本策略與 gate。
2. `.github/workflows/ci.yml` 執行 root docs / production contract / race / govulncheck / Docker smoke。
3. `production-api-worker` 提供可執行的 API + worker + Postgres + metrics 範例。
4. `docs/index.html` 由整合視覺課程同步到 GitHub Pages 入口。

缺口是 diagnostics workflow 還不完整。效能章節提到 pprof，runbook 提到事故診斷，但程式沒有：

- `ENABLE_PPROF` 類型的顯式開關。
- `PPROF_TOKEN` 或沿用 `API_KEY` 的認證策略。
- 預設關閉時 `/debug/pprof/` 回 404 的合約測試。
- 啟用但未授權時回 401 的合約測試。
- runbook 說明如何短期抓 profile，診斷後關閉。
- CI 檢查避免日後文件、測試與實作脫鉤。

## 4. Configuration 審查

現有 config loader 已具備 `PORT`、`QUEUE_SIZE`、`WORKERS`、DB pool、`API_KEY` 與 OTLP endpoint 驗證。下一步應補：

| 設定 | 建議 | 原因 |
|---|---|---|
| `ENABLE_PPROF` | 預設 `false`，必須 parse bool | debug endpoint 不應常態開啟 |
| `PPROF_TOKEN` | trim 後使用；空值時可沿用 `API_KEY` | 避免額外 secret 管理成本，也允許獨立 diagnostics token |
| 啟用條件 | `ENABLE_PPROF=true` 且 `PPROF_TOKEN` / `API_KEY` 至少一個有值 | 防止無認證 pprof 進入 production |

## 5. Verification 建議

本輪應新增或更新下列驗證：

| Gate | 指令 | 預期 |
|---|---|---|
| Config contract | `cd production-api-worker && go test ./internal/config -count=1` | `ENABLE_PPROF=true` 未設定 token fail fast |
| API diagnostics contract | `cd production-api-worker && go test ./internal/api -run 'TestPprofDiagnosticsContract' -count=1` | 預設 404、未授權 401、合法 token 200 |
| Static docs gate | `node scripts/check-pprof-contract.mjs` | README、runbook、Go tests、CI 與實作都有 pprof contract |
| Full production tests | `cd production-api-worker && GOFLAGS='-ldflags=-linkmode=external' go test ./... -count=1` | macOS linker 環境下完整通過 |
| Docs index sync | `node scripts/fix-docs-index-links.mjs --sync-source && node scripts/fix-docs-index-links.mjs --check` | Pages 入口同步整合課程 |

## 6. Troubleshooting 風險

| 風險 | 說明 | 修正方向 |
|---|---|---|
| pprof endpoint 裸露 | heap、goroutine、cmdline、trace 可能暴露內部資訊 | 預設關閉，啟用時要求 Bearer token 與來源網段限制 |
| `go tool pprof` 無 token | 直接抓遠端 URL 不易帶 Bearer header | 用 `curl -H 'Authorization: Bearer ...'` 下載 profile，再用 `go tool pprof profile.pb.gz` |
| 診斷設定永久化 | incident 期間臨時開關可能忘記關閉 | runbook 要寫明診斷後關閉 `ENABLE_PPROF` |
| 文件與實作漂移 | 教材寫安全邊界但 code 未測 | 新增 `scripts/check-pprof-contract.mjs` 與 CI gate |

## 7. Best Practices

1. pprof 是 incident diagnostics，不是公開 API。
2. 先用 metrics / SLI 判斷症狀，再抓 profile。
3. profile 檔案可能含敏感資訊，不提交 repo。
4. 每次新增 debug endpoint 都要有「預設關閉、啟用條件、認證、測試、runbook、關閉流程」。
5. 教材範例要同時展示本機簡化做法與 production 安全做法，避免學習者把 demo pattern 直接部署。

## 8. 結論

本輪最小安全修正是補上 `production-api-worker` 的 pprof diagnostics contract。這不需要大幅改架構，卻能把效能章節、operational runbook、API security 與 CI gate 串起來，讓教程從「知道 pprof」進一步到「知道如何安全地在 production 事故中使用 pprof」。
