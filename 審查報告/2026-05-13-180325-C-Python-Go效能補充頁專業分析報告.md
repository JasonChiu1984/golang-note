## 工程內容校閱

### 速度比較

目前寫法將 C、Python、Go 的速度差異拆成 CPU-bound、I/O-bound、啟動時間、記憶體與併發服務，方向正確。特別是頁面已明確註記「不是固定 benchmark 數字」，這是必要的工程風險控制。

需要補強的是 benchmark reproducibility。若此頁要變成正式專業分析教材，建議新增一組最小但可重跑的測試：

| 測試 | C | Python | Go | 目的 |
|---|---|---|---|---|
| CPU loop | `clang -O2` | CPython pure loop | `go test -bench` | 比較 interpreter overhead 與 native code |
| File I/O | `read/write` with fixed buffer | `open/read/write` | `bufio.Reader/Writer` | 比較 syscall 次數與 buffer 策略 |
| TCP echo | epoll 或 blocking baseline | asyncio baseline | netpoller baseline | 比較 connection concurrency |

### System call 分析

System Call Path 圖解方向正確，因為它沒有把語言速度孤立討論，而是放回 user space、runtime、kernel boundary、device/network 的完整路徑。這對工業自動化教材尤其重要：PLC response time、serial latency、network jitter 與 timeout policy 往往比單次 syscall overhead 更影響結果。

需補充的風險：

| 風險 | 說明 |
|---|---|
| 平台差異 | Linux `strace`、macOS `dtruss`、Windows ETW / ProcMon 工具不同 |
| 權限限制 | macOS 上 `dtruss` 可能受 SIP / sudo 權限影響 |
| 高頻 syscall | 真正問題常是大量小 I/O 或逐筆 FFI，而不是單次 syscall |
| FFI 邊界 | Python C extension、Go cgo 若逐筆跨邊界呼叫，會放大 overhead |

### 應用案例

目前案例選得合理：

| 案例 | 適配度 | 評語 |
|---|---|---|
| PLC / DDC 邊緣資料採集 | 高 | Go 作 gateway、C 作 driver、Python 作測試與資料清洗，定位清楚 |
| 資料分析與 AI 前處理 | 高 | Python 作主工具合理，Go / C 作穩定化與熱路徑補強 |
| SCADA / API 後端服務 | 高 | Go 作長駐 API / worker service 的理由充分 |

建議新增「工業部署檢查表」，讓案例更符合現場工程使用：

| 項目 | 建議補充 |
|---|---|
| IO mapping | 例：PLC register / BACnet object / MQTT topic 對應 |
| Signal flow | sensor -> gateway -> queue -> API -> historian |
| Timeout | per-device timeout、overall polling cycle timeout |
| Retry | transient network error 與 device fault 要分開 |
| Alarm | timeout、stale data、bad quality、queue backlog |
| Fail-safe | stale value 不應直接驅動控制輸出 |
| Maintenance | log correlation、device inventory、firmware / protocol version |
