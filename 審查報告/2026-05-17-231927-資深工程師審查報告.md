## 1. Overview

v1.0.34 已補齊 production API 的 per-client rate limit contract，包含 `RATE_LIMIT_REQUESTS_PER_MINUTE`、`429 rate_limited`、OpenAPI、Go tests、README 與 CI gate。以專案開發深度與廣度來看，教材已具備 API security、pprof、OpenAPI、Prometheus、OTLP collector、rate limit、migration、DB pool、request timeout、panic recovery、worker shutdown 與 runbook 等 production-ready 教學骨架。

本輪重新審查後，最高價值缺口集中在兩個部署邊界：

1. Rate limit 的 client IP 若部署在 reverse proxy / ingress 後方，需要明確定義 `X-Forwarded-For` 信任邊界，否則外部 client 可能偽造來源 IP。
2. 文件已宣告 SIGINT/SIGTERM graceful shutdown，但 `api-worker` 需要可測的 shutdown signal contract，避免只處理 local Ctrl+C 而漏掉 Docker / Kubernetes 常見的 SIGTERM。

Go 官方 Release History 已於本輪查核，最新穩定 patch 仍為 `go1.26.3`（2026-05-07 發布），因此 README 目前以 `Go 1.26.3` 作為教材基準仍合理。

## 2. Architecture

| 層級 | 現況 | 風險 | 建議 |
|---|---|---|---|
| Rate limiter | 已以 client IP 做 fixed window | 若直接信任 `X-Forwarded-For`，外部直連可偽造來源 | 新增 `TRUSTED_PROXY_CIDRS`，只有信任 proxy 來源才採用 forwarded IP |
| Config | 已集中驗證 port、queue、DB pool、pprof、rate limit | proxy CIDR 若不驗證，錯誤部署會在流量進來後才暴露 | 啟動時解析 CIDR，格式錯誤 fail fast |
| Handler | 已有 rate limit middleware | rate limit key 的信任策略未固定 | 新增 trusted proxy contract test |
| Lifecycle | 已有 readiness draining、HTTP shutdown、queue drain | SIGTERM 未被測試固定時，rolling deploy 可能跳過 graceful shutdown | 新增 `monitoredSignals()` 與 `TestMonitoredSignalsContract` |
| CI / Docs | 已有多個 contract gate | 新增部署邊界若不進 CI，後續容易漂移 | 更新 rate-limit check，新增 shutdown-signal check |

## 3. Configuration

| 項目 | 建議合約 |
|---|---|
| `TRUSTED_PROXY_CIDRS` | comma-separated CIDR；空值代表不信任任何 `X-Forwarded-For` |
| Rate limit key | 預設使用 TCP `RemoteAddr`；只有 trusted proxy 來源才採用 `X-Forwarded-For` 第一個 IP |
| Shutdown signals | `SIGINT` 與 `SIGTERM` 都必須進入 readiness draining -> HTTP shutdown -> queue drain |
| Failure behavior | `TRUSTED_PROXY_CIDRS=not-a-cidr` 應 fail fast |

## 4. Workflow

1. Config 載入 `TRUSTED_PROXY_CIDRS`，逐一驗證 CIDR。
2. API handler 建立 trusted proxy config。
3. Rate limiter 先判斷 `RemoteAddr` 是否落在 trusted CIDR。
4. 未信任來源一律使用 `RemoteAddr`，忽略 `X-Forwarded-For`。
5. 信任來源才採用 `X-Forwarded-For` 第一個 IP 作為 rate limit key。
6. `api-worker` 以同一組 signal set 監聽 SIGINT/SIGTERM。
7. 收到 signal 後標記 readiness draining，關閉 HTTP server，最後 drain queue。

## 6. Troubleshooting

| 症狀 | 可能原因 | 處置 |
|---|---|---|
| 所有 client 被視為同一 IP | service 只看到 reverse proxy `RemoteAddr` | 將 proxy 內部 CIDR 加入 `TRUSTED_PROXY_CIDRS` |
| 外部 client 可繞過 rate limit | 直接信任 `X-Forwarded-For` | 保持 `TRUSTED_PROXY_CIDRS` 空值或只允許內部 proxy CIDR |
| Docker / Kubernetes 停止時未 drain | SIGTERM 未被 signal set 捕捉 | 執行 `TestMonitoredSignalsContract` 與 shutdown signal check |
| config 啟動失敗 | CIDR 格式錯誤 | 修正為 `10.0.0.0/8,192.168.10.0/24` 類型格式 |

## 7. Best Practices

| 原則 | 說明 |
|---|---|
| 不預設信任 forwarded header | `X-Forwarded-For` 是可偽造 header，必須由 trusted proxy 邊界保護 |
| signal set 要可測 | SIGINT 代表本機 Ctrl+C，SIGTERM 才是多數容器停止與 rolling deploy 的主要訊號 |
| 文件與測試同步 | deployment contract 不應只寫在 README，需有 Go test 與 Node contract check |
| 保留 health endpoint | shutdown 時 `/readyz=503`，但 `/livez` 可維持 200，讓 orchestrator 區分 draining 與 crash |

## 8. Risk Notes

| 風險 | 狀態 |
|---|---|
| 多層 proxy 的 `X-Forwarded-For` 清理仍取決於 proxy 設定 | 已在 runbook/API contract 標示，教材只固定 application 信任邊界 |
| memory rate limiter 仍非多副本全域限速 | 可接受；正式多副本需 gateway、Redis 或 service mesh |
| 真實 SIGTERM e2e 需容器或 process-level 測試 | 本輪先以 signal set unit test 與 contract check 固定實作入口 |
