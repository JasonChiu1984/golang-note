## 1. Overview

`v1.0.33` 已把 OpenTelemetry collector 從「程式碼中有 trace」推進到「collector receiver / exporter / Compose endpoint / CI gate 可驗證」。以專案開發深度來看，教材已具備 API contract、security、pprof diagnostics、Prometheus、OpenAPI、OTLP collector、migration、DB pool、shutdown、retry cancellation 與 CI 的主軸。

本輪剩餘的最高價值缺口是 **production API 缺少可測的 per-client rate limit 合約**。目前 API 已有 `API_KEY` 與 pprof 防護，但缺少容量保護邊界：同一 client 若持續打 `/jobs`，教材沒有教學用的節流設定、HTTP 429 錯誤 envelope、`Retry-After` header、OpenAPI response 與 contract test。

## 2. Architecture

建議採用最小且可教學的 app-layer rate limit：

| 層級 | 建議 |
|---|---|
| Config | 新增 `RATE_LIMIT_REQUESTS_PER_MINUTE`，預設 `120`，錯誤值 fail fast |
| API middleware | 以 client IP 做固定時間窗限速，保護 `/jobs` 與 `/jobs/{id}` |
| Error contract | 超限回 `429 Too Many Requests`、`error.code=rate_limited`、`Retry-After: 60` |
| OpenAPI | `POST /jobs`、`GET /jobs/{id}` 補 `429` response |
| Docs | README、production README、API contract、runbook、章節與整合視覺課程同步 |
| Verification | `TestRateLimitContract`、`scripts/check-rate-limit-contract.mjs`、Makefile 與 GitHub Actions gate |

## 3. Workflow

修正流程應依下列順序執行：

1. 先補 `internal/config` 設定與錯誤驗證。
2. 再補 API middleware 與 per-IP window limiter。
3. 接著補 Go contract test，固定 status、header、request id 與 error code。
4. 同步 OpenAPI、API contract、README、runbook、章節與整合課程。
5. 新增靜態檢查腳本與 CI gate。
6. 重新同步 `docs/index.html`，再做版本、tag 與 push。

## 4. Configuration

新增設定建議如下：

| Env | 預設 | 驗證 | 用途 |
|---|---:|---|---|
| `RATE_LIMIT_REQUESTS_PER_MINUTE` | `120` | 正整數 | 每 client IP 每分鐘 `/jobs` / `/jobs/{id}` 額度 |

錯誤設定如 `RATE_LIMIT_REQUESTS_PER_MINUTE=0` 或非數字字串，應在啟動階段 fail fast，不應靜默改回預設值。

## 6. Troubleshooting

| 症狀 | 可能原因 | 處置 |
|---|---|---|
| API 回 `429 rate_limited` | 同一 client IP 超過 `RATE_LIMIT_REQUESTS_PER_MINUTE` | 檢查 caller、gateway、重試策略與 `Retry-After` |
| staging 未重現 rate limit | 反向代理未正確傳 `X-Forwarded-For` 或測試來源 IP 不一致 | 明確記錄 proxy trust boundary |
| OpenAPI 檢查失敗 | spec 未補 `429` 或 `rate_limited` enum | 同步 `api/openapi.yaml` 與 API contract |
| config test 失敗 | env 驗證未納入 rate limit | 補 `DefaultRateLimitPerMinute` 與 invalid config case |

## 7. Best Practices

- App-layer rate limit 應視為第二層保護；正式環境仍應搭配 API gateway、Ingress、WAF 或 service mesh。
- Health endpoint 不應被 app rate limit 擋住，否則可能造成 orchestrator 誤判服務死亡。
- 429 response 要保留 `X-Request-ID`，方便 client report、log、trace 與 incident review 對齊。
- OpenAPI、Go contract test 與 README 必須一起改，避免教學文件與可執行合約漂移。

## 8. Risk Notes

| 風險 | 等級 | 說明 |
|---|---|---|
| 反向代理 IP 信任邊界 | 中 | `X-Forwarded-For` 在正式環境需由可信 proxy 覆寫，不能盲信外部 client |
| in-memory limiter 重啟歸零 | 低 | 教材可接受；多副本正式部署需改用 gateway 或共享狀態 |
| 額度與真實 SLA 不一致 | 中 | `120/min` 是教學預設，正式環境需依流量與 queue / DB 容量重算 |
| 非硬體 / 外部平台驗證 | 低 | 本輪不宣稱已完成 gateway、Kubernetes、Alertmanager 或正式 APM 驗證 |

## 9. 結論

本教程的專案開發深度已高於一般入門教材。`v1.0.34` 應補上的不是新語法，而是 production API 的容量保護合約：讓 rate limit 從文字建議變成 config、middleware、OpenAPI、contract test、CI 與文件一致的可驗證交付。
