## 2. 本輪發現的主要缺口

### P1：Worker queue shutdown 存在 close/send 競態風險

`production-api-worker/internal/worker/queue.go` 的 `Enqueue` 先讀取 `closed`，再釋放 mutex，接著對 `q.jobs` channel 送入 task。`ShutdownContext` 則會在另一條 goroutine 中 close 同一個 channel。

這代表下列 interleaving 有機會發生：

```text
goroutine A: Enqueue 讀到 closed=false
goroutine A: 釋放 mutex
goroutine B: ShutdownContext 設 closed=true 並 close(q.jobs)
goroutine A: q.jobs <- task
結果：panic: send on closed channel
```

這不是單純教學文字缺漏，而是 production service shutdown path 的實作風險。尤其 API 已經具備 readiness / draining 文件，若 queue 本身仍可能在 shutdown 期間 panic，服務生命週期教學就不完整。

## 3. 建議修正方向

| 項目 | 建議 |
|---|---|
| Queue 同步邊界 | `closed` 檢查、channel send、channel close 必須共用同一個 mutex 或由單一 owner 控制 |
| 穩定錯誤 | shutdown 後的新 enqueue 應回穩定錯誤，例如 `worker.ErrClosed` |
| 測試 | 新增 close 後 enqueue 與 concurrent enqueue + shutdown 測試 |
| 可測性 | `internal/worker` 不應為了測 queue 而強制載入 Prometheus / OpenTelemetry；建議改成小型 observer interface |
| 教材同步 | README、第 7 章、第 11 章、速查表、康乃爾筆記與 `production-api-worker` 文件都應補上 queue shutdown safety |

## 4. 風險說明

| 風險 | 等級 | 說明 |
|---|---:|---|
| shutdown 期間 panic | 高 | 可能導致 process 異常結束，破壞 graceful shutdown 目標 |
| 測試依賴外部 module | 中 | worker package 測試被 observability 依賴拖住，離線 sandbox 無法聚焦驗證 queue 行為 |
| 文件與實作不一致 | 中 | 教材已教 readiness / drain，但 queue close/send 邊界未明確化 |

## 5. 本輪更新決策

採取最小安全修正：

1. `Queue.Enqueue` 持有 mutex 完成 `closed` 檢查與 non-blocking send。
2. `Queue.ShutdownContext` 使用同一把 mutex 設定 `closed` 並 close channel。
3. 新增 `worker.ErrClosed` 作為 shutdown 後 enqueue 的穩定錯誤。
4. 將 worker 對 observability 的依賴改成 `Observer` 小介面，讓 worker 測試不必載入完整 Prometheus / OTel。
5. 新增 shutdown safety 測試與教材同步說明。
