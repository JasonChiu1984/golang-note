> 建議更新版本：v1.0.34

## 1. Overview

v1.0.33 已把 OpenTelemetry collector contract 固定成可重跑的教學 gate，包含 OTLP gRPC receiver、debug exporter、Docker Compose endpoint、runbook、README 與 CI 檢查。以專案開發深度與廣度來看，本教程已經從語法課程提升到 production API skeleton：具備 config validation、DB pool、migration、OpenAPI、security、pprof、Prometheus、OTLP collector、Docker Compose smoke 與 GitHub Actions release gate。

本輪仍可補強的最高價值缺口是 API rate limit contract。`production-api-worker` 已有 bounded queue 與 queue full 回應，但 HTTP 邊界尚未用可測設定保護單一 client 過量呼叫；這會讓讀者誤以為 backpressure 只在 service / queue 層處理，而忽略 production API 常見的入口限速、穩定錯誤格式與 OpenAPI 契約。

## 2. Architecture

| 層級 | 現況 | 風險 | 建議 |
|---|---|---|---|
| HTTP middleware | 已有 request id、recover、auth、security headers、metrics | 缺少 request rate protection，單一 client 可持續壓入 queue | 新增 per-client IP fixed-window rate limiter |
| Config | 已集中驗證 `PORT`、queue、DB pool、auth、pprof | 限速值若散落在 handler 內，不利部署調整 | 新增 `RATE_LIMIT_REQUESTS_PER_MINUTE` 並 fail fast |
| API contract | OpenAPI 已固定 endpoint、schema、auth、error envelope | `429 rate_limited` 未出現在 machine-readable spec | 更新 OpenAPI 與 API contract 文件 |
| Testing | handler contract tests 已覆蓋 request id、timeout、auth、pprof | rate limit header、status code、error code 未被測試固定 | 新增 `TestRateLimitContract` |
| CI / Docs | 已有 OpenAPI、pprof、OTLP collector gate | 文件、Compose env、測試入口可能漂移 | 新增 `check-rate-limit-contract.mjs` 與 Makefile / CI gate |

## 3. Configuration

建議固定下列本地教學 contract：

| 項目 | 固定值 |
|---|---|
| Env var | `RATE_LIMIT_REQUESTS_PER_MINUTE` |
| 預設值 | `120` |
| 限速範圍 | 每個 client IP、每分鐘 |
| 保護 endpoint | `/jobs`、`/jobs/{id}`；pprof diagnostics 也沿用 middleware 防止 debug endpoint 被濫用 |
| 不限速 endpoint | `/livez`、`/readyz`、`/metrics` |
| 超限狀態碼 | `429 Too Many Requests` |
| Error code | `rate_limited` |
| Header | `Retry-After: 60`、保留 `X-Request-ID` |
| 驗證入口 | `node scripts/check-rate-limit-contract.mjs`、`make rate-limit-check` |

## 5. Troubleshooting

| 症狀 | 可能原因 | 處置 |
|---|---|---|
| 所有 client 都被同一個 IP 限速 | 反向代理未傳遞或未清理 `X-Forwarded-For` | 正式環境應在 trusted proxy / gateway 層統一 client IP 規則 |
| health check 被限速 | middleware 套用範圍過大 | 確認 `/livez`、`/readyz` 不在 rate limit 範圍 |
| OpenAPI 沒有 429 | 只改 Go handler，未同步 contract | 跑 `node scripts/check-rate-limit-contract.mjs` |
| 設定為 0 或負數仍啟動 | config validation 缺漏 | `RATE_LIMIT_REQUESTS_PER_MINUTE` 必須為正整數 |

## 6. Best Practices

| 原則 | 說明 |
|---|---|
| 入口限速不取代 queue backpressure | HTTP rate limit 先擋單一 client；bounded queue 仍處理整體服務壓力 |
| health endpoint 不限速 | LB / orchestrator 探測不能被業務流量誤傷 |
| error envelope 穩定 | 429 仍使用 `{error:{code,message}}`，讓前端與 SDK 可一致處理 |
| 正式環境放在 gateway 更佳 | 本 repo 示範應用層 contract；production 可加 API gateway / WAF / Envoy rate limit |

## 7. Risk Notes

| 風險 | 狀態 |
|---|---|
| fixed-window limiter 不是企業級分散式限速 | 可接受；本輪目標是單節點教學 contract |
| `X-Forwarded-For` 信任邊界需由正式部署定義 | 已列為 deployment risk；後續可補 trusted proxy 章節 |
| limiter map 清理策略尚未企業化 | 教學流量可接受；高基數 client 應改 LRU / TTL / gateway |

## 8. Summary

本輪建議更新目標是 v1.0.34：補上 Rate limit contract，讓 production API 從「queue 滿載才回壓」提升為「HTTP 入口、設定、OpenAPI、測試、README、CI 都能固定 per-client request protection」。
