## 結論

本教程針對專案開發的深度與廣度已符合 production service 教學骨架：目前已覆蓋 OpenAPI、readiness、request decoding、idempotency key、API key security、CORS、request body limit、HTTP timeout、rate limit、trusted proxy、DB pool、migration、retry cancellation、queue backpressure、worker failure、observability、runbook、CI quality、docs publishing、ReleaseNote、dependency governance 與 Compose smoke。

本次重看後，主要缺口不是新增語法主題，而是 HTTP API latency metrics 還沒有被 formal contract gate 固定。現有 metrics 有 `api_requests_total`、`worker_queue_depth`、`worker_jobs_total` 與 `worker_job_duration_seconds`，但缺少 `api_request_duration_seconds` 這類按 route / method / status 標籤切分的 API latency histogram。這會讓 SLO、Prometheus alert、incident review 只能看請求量與 worker latency，無法直接判斷 handler、auth、rate limit、request decoding 或 storage path 的 API 延遲。

## 需要更新的部分

1. 新增 API latency metrics contract gate，固定 `api_request_duration_seconds` histogram。
2. 在 observability 層增加 `RequestDuration` histogram，標籤需包含 `route`、`method`、`status`。
3. 在 HTTP metrics middleware 觀測每個 request 的 duration，並保留既有 `api_requests_total` counter。
4. 新增 Go contract test，確認 `/metrics` 同時輸出 `api_requests_total` 與 `api_request_duration_seconds`。
5. 同步 README、production README、API contract、OpenAPI、第 7 / 9 / 11 章、Cheatsheet、整合視覺課程、Makefile、GitHub Actions、VERSION、CHANGELOG 與 `docs/index.html`。

## 風險與驗證建議

- 風險：若只在 Prometheus alert 或 runbook 提到 latency，而 runtime 沒有 histogram，事故時仍無法用 metrics 判斷 API handler 延遲。
- 風險：若 histogram 沒有 route / method / status labels，會難以分辨 `/jobs` 建立、查詢、`/metrics` scrape 或錯誤分支延遲。
- 驗證：需執行 `node scripts/check-api-latency-metrics-contract.mjs`、所有 root `scripts/check-*-contract.mjs`、`cd production-api-worker && make api-latency-metrics-check`、`make ci-contract`、production Go tests、docs index sync/check 與 HTML home link check。
