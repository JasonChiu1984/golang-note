# 資深工程師審查報告：Golang 學習筆記 v1.0.33 後續補強

> 審查日期：2026-05-17
> 完整日期時間：2026-05-17 20:42:15 CST +0800
> 審查角色：資深 Go / backend / production readiness reviewer
> 目前版本：v1.0.33
> 建議更新版本：v1.0.34

## 1. Overview

v1.0.33 已將 OpenTelemetry collector 從文件描述提升為可重跑 contract，包含 `otel-collector.yaml`、Compose endpoint、`debug exporter`、Makefile、CI 與 runbook gate。以專案開發深度與廣度來看，教材已具備 production API 教學骨架：OpenAPI、API key、pprof、Prometheus、OTLP collector、migration、DB pool、request timeout、panic recovery 與 Docker Compose smoke。

本輪重新審查後，最高價值缺口是 production API 仍缺少可測的 per-client rate limit。若教材要示範接近真實服務的過載保護，只靠 queue size、timeout 與 API key 不足；`/jobs` 與 `/jobs/{id}` 需要明確的限速行為、穩定錯誤碼、OpenAPI 記錄、設定驗證與 CI gate。

Go 官方基準已於本輪重新查核：官方 Release History 仍列出 `go1.26.3` 與 `go1.25.10` 於 2026-05-07 發布，因此本教材目前保留 `Go 1.26.3` 作為基準是合理的。

## 2. Architecture

| 層級 | 現況 | 風險 | 建議 |
|---|---|---|---|
| API handler | 已有 auth、security headers、metrics、panic recovery、timeout contract | 單一 client 可持續壓測 business endpoint | 在 handler middleware 補上 per-client IP rate limit |
| Config | 啟動設定已 fail fast 驗證 DB pool / pprof 等項目 | 限速若只寫死在程式碼，部署容量不可調 | 新增 `RATE_LIMIT_REQUESTS_PER_MINUTE` 並驗證正整數 |
| API contract | OpenAPI 已固定多數錯誤碼與 schema | `429` 行為缺少 machine-readable contract | OpenAPI 補上 `429 rate_limited` |
| Tests | contract tests 已涵蓋 auth、pprof、panic、timeout | 限速邊界無 regression test | 新增 `TestRateLimitContract` |
| Docs / CI | README 與 CI 已有多個 gate | 新增能力若未納入 gate，後續容易漂移 | 新增 `scripts/check-rate-limit-contract.mjs`、Makefile 與 GitHub Actions gate |

## 3. Configuration

| 項目 | 建議合約 |
|---|---|
| Env | `RATE_LIMIT_REQUESTS_PER_MINUTE` |
| Default | `120` |
| Scope | `/jobs`、`/jobs/{id}` |
| Public routes | `/livez`、`/readyz` 不受限速影響 |
| Key | client IP；正式 reverse proxy 需明確管理 `X-Forwarded-For` 信任邊界 |
| Error status | `429 Too Many Requests` |
| Error code | `rate_limited` |
| Header | `Retry-After: 60` |

## 4. Workflow

1. Config 載入階段驗證 `RATE_LIMIT_REQUESTS_PER_MINUTE`。
2. Handler 建立 `rateLimiter`，依 client IP 計算固定時間窗。
3. Business endpoint 先通過 auth，再進入 rate limit middleware。
4. 超限時回穩定 JSON error envelope，保留 `X-Request-ID` 與 `Retry-After`。
5. OpenAPI、README、runbook、章節與 CI 同步標記此 contract。

## 6. Troubleshooting

| 症狀 | 可能原因 | 處置 |
|---|---|---|
| 正常 client 被限速 | reverse proxy 將所有 request 顯示為同一 IP | 明確設定與審查 `X-Forwarded-For` 信任邊界 |
| 測試環境出現 429 | 壓測或 e2e 測試未調高限速 | 測試環境設定較高的 `RATE_LIMIT_REQUESTS_PER_MINUTE` |
| OpenAPI 與實作不一致 | 新增錯誤碼後未更新 spec | 執行 `node scripts/check-rate-limit-contract.mjs` 與 OpenAPI gate |
| health check 被誤限速 | middleware scope 過寬 | 確認 `/livez`、`/readyz` 不進入限速分支 |

## 7. Best Practices

| 原則 | 說明 |
|---|---|
| 限速先保護 business endpoint | health / readiness 需維持部署系統可觀測性 |
| 錯誤碼穩定 | client 應依 `error.code=rate_limited` 與 HTTP 429 判斷重試 |
| 設定 fail fast | 無效限速值不可 silent fallback，避免部署後才暴露容量錯誤 |
| 文件與 OpenAPI 同步 | 限速是對外合約，不是內部實作細節 |

## 8. Risk Notes

| 風險 | 狀態 |
|---|---|
| 本地 memory limiter 不適合多副本全域限速 | 可接受；本教材先示範單 process contract，多副本需 Redis / gateway / service mesh |
| `X-Forwarded-For` 信任邊界需正式部署決策 | 已在 API contract 與文件標註 |
| 固定時間窗可能有邊界突增 | 教學可接受；後續可延伸 token bucket / leaky bucket |

## 9. Summary

本輪建議更新目標是 v1.0.34：補上 Rate limit contract，使 production API 具備可測、可文件化、可由 OpenAPI 與 CI 固定的 per-client 過載保護行為。
