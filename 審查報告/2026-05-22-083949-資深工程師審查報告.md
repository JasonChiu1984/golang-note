## 4. Configuration Review

`API_KEY` 設計符合教學用最小 production security contract：

| 設定 | 合約 |
|---|---|
| `API_KEY=""` | local teaching mode，不要求 token |
| `API_KEY` 有值 | `/jobs`、`/jobs/{id}`、`/metrics` 要求 `Authorization: Bearer <token>` |
| `/livez`、`/readyz` | 永遠公開，保留 LB / orchestrator 探測 |
| 安全標頭 | 所有 response 固定基本安全標頭 |

缺口不是 handler 行為，而是缺少與 request correlation 同等級的 static gate。

## 6. Troubleshooting

| 可能問題 | 原因 | 建議修正 |
|---|---|---|
| `/readyz` 回 401 | auth middleware 把 health probe 誤列為 protected endpoint | static gate 應檢查 requiresAuth 邊界 |
| `/metrics` 無 token 仍公開 | API security 文件與 handler 漂移 | static gate 應檢查 Go tests 與 OpenAPI |
| OpenAPI 顯示 health endpoint 需要 Bearer auth | global security 未被 route 覆寫 | static gate 應檢查 `/livez`、`/readyz` 的 `security: []` |
| 文件提到 API_KEY，但 CI 未檢查 | 缺少 Makefile / GitHub Actions gate | 新增 `api-security-check` 與 CI step |

## 7. Best Practices

- 教學專案可用 `API_KEY` 示範最小安全邊界，但需明確說明它不取代 OAuth2、mTLS、API gateway 或 IAM。
- Health probe 不應被業務 token 擋住，否則部署平台無法判斷 readiness / liveness。
- Metrics endpoint 在正式環境通常不應裸露；若使用 Prometheus scrape，需規劃 bearer token file、network policy 或 sidecar gateway。
- 安全標頭應由 middleware 統一設定，避免個別 handler 漏設。
- 文件、OpenAPI、Go tests、Makefile、CI 必須以靜態 gate 綁在一起，避免教程重整造成合約退化。

## 8. Risk Notes

本輪不建議導入 OAuth2、JWT、mTLS 或 API gateway 範本，原因是目前教程目標是 Go production skeleton，不是完整 IAM 平台。最小安全合約先固定 `API_KEY` / Bearer token / public probes / security headers，較符合小步發布與教學可維護性。
