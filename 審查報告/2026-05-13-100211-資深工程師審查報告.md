## 總結

本教程目前已具備足夠的專案開發深度與廣度：基礎語法、併發、部署、效能、測試與兩個專案實戰路線已形成完整學習閉環。`production-api-worker` 也已覆蓋 API contract、request correlation、readiness/drain、panic recovery、observability 與 transaction boundary。

本輪找到的主要缺口是 request decoding 邊界仍未完全可測化。API contract 已宣告「JSON 無法解析」應回 `400 invalid_input`，但 handler 直接把 `json.Decoder` 錯誤交給統一錯誤轉換層時，會被視為未分類錯誤並回 `500 internal_error`。此外，unknown field、trailing JSON value 與空白 `name` 尚未被明確納入合約測試。

## 具體缺失

| 編號 | 缺失 | 影響 |
|---|---|---|
| R1 | `POST /jobs` 的 malformed JSON 錯誤未包成 `domain.ErrInvalidInput` | client input error 可能被誤分類為 server fault |
| R2 | request decoder 未拒絕 unknown field | client typo 可能被靜默忽略，造成相容性問題延後暴露 |
| R3 | request decoder 未檢查 trailing JSON value | 只 decode 第一個 JSON object 後放過多餘資料，合約邊界不清楚 |
| R4 | `name` 只有空白時仍可能通過非空字串檢查 | 必填欄位語意與 API contract 的「不可為空」不一致 |
| R5 | 第 7 / 11 章與速查表未說明 request decoder 錯誤分類也是 API 合約 | 讀者容易只測成功 response 與 domain error，而漏掉 parser edge case |

## 建議修正

1. 在 `production-api-worker/internal/api/handler.go` 建立獨立 request decode gate。
2. 使用 `json.Decoder.DisallowUnknownFields()` 拒絕未知欄位。
3. Decode 後再檢查是否還有第二個 JSON value，避免 trailing payload。
4. 將 decoder 錯誤全部包成 `domain.ErrInvalidInput`，讓 handler 穩定回 `400 invalid_input`。
5. 在 domain validation 中以 `strings.TrimSpace(name)` 判斷必填欄位。
6. 新增 `TestRequestDecodingContract`，固定 malformed JSON、unknown field、trailing JSON value 與空白 name。
7. 同步更新 README、API contract、第 7 / 11 章、Cheat Sheet 與康乃爾筆記。

## 審查結論

本輪不是新增大功能，而是把 production API 最前面的輸入邊界收斂成可驗證合約。這能提升教程的專案開發深度，因為真實服務的可靠性不只來自 service layer，也來自 handler 對 parser、schema 與錯誤分類的明確約束。
