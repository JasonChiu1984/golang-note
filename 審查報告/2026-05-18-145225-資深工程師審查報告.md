## 1. Overview

以資深工程師角度重新檢視後，教材在語法、專案架構、CI、OpenAPI、Observability、pprof、rate limit、trusted proxy 與 shutdown signal 的深度已接近 production training material。最新基準 `v1.0.36` 已完成 automation record 與版本標示，但工作樹內仍保留一組高價值、可本地驗證的 CORS allowlist 實作與文件草稿，尚未成為已提交、已標籤、可由 GitHub Pages 與 CI 重跑的正式交付。

本輪最高價值修正是將 CORS allowlist contract 正式發布為 `v1.0.37`，避免前端跨域教學只停留在文字建議，或被誤簡化成 `Access-Control-Allow-Origin: *`。

## 2. Architecture

| 面向 | 現況 | 審查判斷 |
|---|---|---|
| API boundary | 已有 API key、rate limit、trusted proxy、OpenAPI 與 error envelope | 缺少瀏覽器同源政策的明確 service-side contract |
| Config boundary | `internal/config` 已集中驗證 env | 應加入 `CORS_ALLOWED_ORIGINS` 並 fail fast 拒絕 wildcard、path、query、fragment 與非 HTTP scheme |
| Handler middleware | 已具備 auth、rate limit、recover、metrics、security headers | 應補上 allowlist 型 CORS middleware，並保持 health / API 語意不漂移 |
| CI / docs | 已有多個 `node scripts/check-*.mjs` contract gate | CORS 也需要同級靜態檢查，避免 README、OpenAPI、Go tests 與 CI 漂移 |

## 3. Workflow

```text
Browser request
-> Origin header exists?
-> Origin in CORS_ALLOWED_ORIGINS exact allowlist?
-> yes: set Access-Control-Allow-Origin + Vary: Origin
-> preflight: return 204
-> actual request: continue through auth / rate limit / handler
-> no and OPTIONS: return 403 without CORS header
-> no and actual request: continue without CORS header
```

這個設計保留 API authentication 與 CORS 的責任分離：CORS 只控制瀏覽器是否允許前端讀取 response，不取代 Bearer token、rate limit、gateway policy 或 WAF。

## 4. Configuration

| 設定 | 預設 | 合約 |
|---|---|---|
| `CORS_ALLOWED_ORIGINS` | 空字串 | 預設不回 CORS header |
| 格式 | comma-separated exact origin | 僅允許 `http` / `https` scheme |
| 禁止格式 | `*`、path、query、fragment、`file://` | 啟動設定階段 fail fast |

正式部署範例：

```bash
CORS_ALLOWED_ORIGINS=https://app.example.com,http://localhost:5173 go run ./cmd/api-worker
```

## 6. Troubleshooting

| 症狀 | 可能原因 | 建議處理 |
|---|---|---|
| 瀏覽器前端回報 CORS error | origin 未列入 `CORS_ALLOWED_ORIGINS` | 檢查 scheme、host、port 是否 exact match |
| 設定後服務無法啟動 | origin 包含 path、query、fragment 或非 HTTP scheme | 改成 `https://app.example.com` 這類 origin 格式 |
| preflight 回 `403` | origin 不在 allowlist | 不要改成 wildcard，應補正部署前端 origin |
| Postman / curl 正常但 browser 不行 | CORS 是瀏覽器 enforcement | 用 browser devtools 檢查 request `Origin` 與 response header |

## 7. Best Practices

- CORS allowlist 應由部署環境明確配置，不應在程式碼內硬編碼正式網域。
- 不要使用 `Access-Control-Allow-Origin: *` 解決 production 前端整合問題。
- CORS 與 API key、rate limit、trusted proxy、gateway auth 是不同層級的控制，需一起設計。
- 文件、OpenAPI、Go contract test、Compose env 與 CI gate 要同步更新，避免教學內容與實際 service 行為分離。

## 8. Risk Notes

本輪可在本地以單元測試與靜態檢查完成，不需要外部瀏覽器或真實 gateway。正式環境仍需由 Ingress / API Gateway / WAF 管理 TLS、cookie policy、credential mode、preflight cache 與外部網域治理。
