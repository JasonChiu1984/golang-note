Modern Stdlib：Go 1.21 / 1.22 / 1.23 版本邊界

新版標準庫把常見集合操作與 HTTP 路由收斂到官方 API；本章明確切開 Go 1.21、Go 1.22 與 Go 1.23+ 的可用 API，避免專案版本假設混淆。

版本本章重點專案判斷
Go 1.21slices / maps 基礎集合工具，例如 slices.Clone、slices.Sort、maps.Clone、maps.Equal。適合降低自寫 helper 數量，但 clone 是 shallow copy。
Go 1.22net/http.ServeMux 支援 method pattern、path wildcard 與 Request.PathValue。中小型 API 可優先用標準庫 router。
Go 1.23+maps.Keys / maps.Values 回傳 iterator，常搭配 slices.Sorted 或 slices.Collect。若專案固定 Go 1.21/1.22，不應直接使用 Go 1.23 iterator API。
Go 1.21

slices：把 slice 操作從手寫迴圈拉回標準庫

適用於排序、複製、刪除、去重、二分搜尋。production code 的重點是語意清楚、避免 aliasing、確認排序前置條件。

API用途工程注意
slices.Clone複製 slice避免修改共用底層 array
slices.Sort排序 ordered 型別會原地修改
slices.Delete刪除區間回傳值要接回原變數
slices.Compact移除連續重複值通常要先排序
slices.BinarySearch二分搜尋slice 必須已排序
 
package main

import (
	"fmt"
	"slices"
)

func main() {
	ids := []int{4, 2, 2, 8, 1}

	sorted := slices.Clone(ids) // 不污染呼叫端傳入的 slice
	slices.Sort(sorted)
	sorted = slices.Compact(sorted)

	pos, ok := slices.BinarySearch(sorted, 4)
	fmt.Println(sorted, pos, ok) // [1 2 4 8] 2 true
}
Step-by-step：如何用在服務層
  1. 接收外部輸入時先 Clone，避免下游排序改到上游資料。
  2. 需要 binary search 前，明確在同一段邏輯中排序。
  3. 刪除、去重後一定接回回傳值，因為長度可能改變。
反例：直接對 request DTO 的 slice 排序，導致後續 middleware 或 log 看到的順序被改掉。
Go 1.21

maps：設定比對、複製與清理

適合處理 feature flags、label set、metadata、測試期望值。注意 map 本身仍不是 concurrency-safe。

API用途工程注意
maps.Clone複製 map避免把內部狀態交給呼叫端修改
maps.Equal比較 key/value適合測試與設定 diff
maps.DeleteFunc依條件刪除清理空值、過期值
版本邊界maps.Keys / maps.Values屬於 Go 1.23+ iterator API，不放進 Go 1.21 假設
 
package main

import (
	"fmt"
	"maps"
)

func sanitizeLabels(in map[string]string) map[string]string {
	out := maps.Clone(in)
	maps.DeleteFunc(out, func(k, v string) bool {
		return k == "" || v == ""
	})
	return out
}

func main() {
	labels := map[string]string{"service": "api", "empty": ""}
	fmt.Println(sanitizeLabels(labels))
}
Step-by-step：metadata 的安全邊界
  1. 進入 domain 前先清理空 key、空 value。
  2. 對外回傳 map 時先 clone，避免呼叫端改壞內部 cache。
  3. 不要依賴 map iteration 順序；輸出前需要排序。
反例：把內部 map 直接回傳給 handler，讓其他 goroutine 同時讀寫造成 data race。
Go 1.23+

maps iterators：Keys / Values 與 slices 收集

Go 1.23 後 maps.Keys 與 maps.Values 回傳 iterator。這很適合輸出排序後的 key list，但專案若仍固定 Go 1.21/1.22，不能直接採用。

API用途工程注意
maps.Keys取得 key iterator輸出順序仍不可依賴
maps.Values取得 value iterator適合搭配 slices.Collect
slices.Sorted收集並排序 iterator適合設定 diff、穩定輸出
 
package main

import (
	"fmt"
	"maps"
	"slices"
)

func main() {
	labels := map[string]string{"service": "api", "env": "prod"}
	keys := slices.Sorted(maps.Keys(labels))
	values := slices.Collect(maps.Values(labels))
	fmt.Println(keys, values)
}
Step-by-step：版本升級時再採用
  1. 先確認 go.mod 與 CI 使用 Go 1.23+。
  2. 需要穩定輸出時用 slices.Sorted(maps.Keys(m))。
  3. 若維持 Go 1.21/1.22，仍用手寫 key slice 再排序。
反例：教材或專案標示 Go 1.21/1.22，卻直接使用 maps.Keys iterator，導致 CI 編譯失敗。
Go 1.22

新版 http.ServeMux：Method + Path Variable

基本 REST API 可以先用標準庫實作。當需要複雜 middleware chain、route group、schema binding 時，再評估第三方 router。

package main

import (
	"fmt"
	"log"
	"net/http"
)

func main() {
	mux := http.NewServeMux()

	mux.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r *http.Request) {
		id := r.PathValue("id")
		fmt.Fprintf(w, "user id=%s", id)
	})

	mux.HandleFunc("POST /users", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusCreated)
	})

	log.Fatal(http.ListenAndServe(":8080", mux))
}
Step-by-step：何時標準 mux 就夠
  1. CRUD API、少量 middleware、路由規則清楚時，先用標準庫。
  2. 把認證、log、timeout 寫成 handler wrapper，不要塞進每個 handler。
  3. 若團隊需要 route group、OpenAPI binding、複雜 middleware graph，再導入 router。
反例：只為了 path variable 就引入大型框架，增加升級與資安維護成本。

Database Layer：database/sql、交易與連線池

資料庫層的核心不是會寫 SQL，而是能控制 timeout、交易邊界、連線池、錯誤分類與 service/repository 分層。

Connection Pool

sql.Open 不是連線：啟動時要 PingContext

sql.Open 建立的是 handle，不代表 DB 可用。服務啟動階段要用 timeout 驗證連線，並設定 pool 邊界。

設定用途常見判斷
SetMaxOpenConns最大開啟連線避免服務把 DB 打爆
SetMaxIdleConns閒置連線數降低熱路徑建立連線成本
SetConnMaxLifetime連線生命週期配合 DB / LB 斷線策略
PingContext啟動健康檢查不可無 timeout 地卡住部署
 
package db

import (
	"context"
	"database/sql"
	"time"
)

func Open(ctx context.Context, driver, dsn string) (*sql.DB, error) {
	db, err := sql.Open(driver, dsn)
	if err != nil {
		return nil, err
	}

	db.SetMaxOpenConns(25)
	db.SetMaxIdleConns(10)
	db.SetConnMaxLifetime(30 * time.Minute)

	pingCtx, cancel := context.WithTimeout(ctx, 3*time.Second)
	defer cancel()
	if err := db.PingContext(pingCtx); err != nil {
		db.Close()
		return nil, err
	}
	return db, nil
}
Step-by-step：pool 參數怎麼談
  1. 先問 DB 最大連線數與同時服務數，避免每個服務各自開太大。
  2. 用 latency、wait count、DB CPU 觀察瓶頸，不靠感覺調。
  3. 部署前讓 readiness check 依賴 Ping，但 liveness 不要過度依賴 DB。
Transaction

defer Rollback：交易保險絲

交易函式只要中途 return error，就讓 rollback 保底；commit 成功後 rollback 會回傳 harmless error，可忽略。

func Transfer(ctx context.Context, db *sql.DB, from, to int64, amount int) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()

	if _, err := tx.ExecContext(ctx,
		"UPDATE accounts SET balance = balance - ? WHERE id = ?",
		amount, from,
	); err != nil {
		return err
	}

	if _, err := tx.ExecContext(ctx,
		"UPDATE accounts SET balance = balance + ? WHERE id = ?",
		amount, to,
	); err != nil {
		return err
	}

	return tx.Commit()
}
Step-by-step：交易邊界放哪裡
  1. 由 service 決定 use case 的交易邊界。
  2. repository 接收 tx 或抽象 executor，不自己偷偷開交易。
  3. 交易內不要呼叫慢速外部 API，避免長時間鎖住資料。
反例：在 repository 每個方法各自開 transaction，導致一次業務操作無法保證原子性。
Architecture

Service / Repository 分層圖解

Handler：只處理 transport concern，不寫 SQL。
Service：決定交易、權限、業務規則與錯誤分類。
Repository：只封裝 SQL 與資料映射。
DB Pool：有 timeout、有上限、有觀測指標。
Step-by-step：避免 N+1 query
  1. 先從 API response shape 找出需要批次讀取的關聯資料。
  2. repository 提供 FindByIDs(ctx, ids)，不要在 loop 裡逐筆查。
  3. 測試中加入 query count 或 fake repository，避免回歸。

Observability：log、metrics、trace 與 debug 邊界

可觀察性不是多印 log，而是讓一次 request 的錯誤、耗時、資源使用與使用者影響可以被串起來。

Structured Logging

log/slog：固定欄位與 request correlation

production log 必須是機器可查詢的欄位，不要只靠自然語言訊息。

package main

import (
	"context"
	"log/slog"
	"os"
)

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
	ctx := context.Background()

	logger.InfoContext(ctx, "order created",
		"service", "checkout",
		"request_id", "req-123",
		"order_id", 991,
		"amount", 1200,
	)
}
Step-by-step：log 欄位設計
  1. 固定欄位：service、env、request_id、user_id、trace_id。
  2. 錯誤欄位：error、error_kind、retryable、status_code。
  3. 避免把密碼、token、完整個資寫進 log。
反例：log.Println("failed") 沒有 request id、沒有錯誤分類，事故時無法查。
Metrics / Trace

Prometheus 與 OpenTelemetry 的工程分工

Metrics 回答「整體是否異常」，Trace 回答「這一次慢在哪裡」。兩者都要靠一致的 service name 與 request correlation。

觀測資料回答問題常用欄位
Counter總量是否上升requests_total、errors_total
Gauge目前狀態inflight_requests、queue_depth
Histogram延遲分佈request_duration_seconds
Trace Span單次請求耗時拆解trace_id、span_id、db.statement
 
func metricsHandler(w http.ResponseWriter, r *http.Request) {
	// 教學用：Prometheus text format 的最小概念。
	// 真實服務通常使用 prometheus client library。
	w.Header().Set("Content-Type", "text/plain; version=0.0.4")
	fmt.Fprintln(w, "# TYPE api_requests_total counter")
	fmt.Fprintln(w, `api_requests_total{method="GET",route="/users/{id}",status="200"} 42`)
}
Step-by-step：trace 怎麼接上 log
  1. request 進來時建立或讀取 trace id。
  2. 每個 log 都帶 trace_id，讓 log search 能跳回 trace。
  3. DB、HTTP client、queue worker 各自建立 span，讓慢點可定位。
Health / pprof

Health Check 與 pprof：可用性和除錯邊界要分開

Endpoint用途Production 邊界
/livez程序是否活著不應依賴 DB，避免錯誤重啟風暴
/readyz是否可接流量可檢查 DB、cache、必要依賴
/metrics供監控系統抓取避免高 cardinality label
/debug/pprof事故剖析 CPU、heap、goroutine必須限制網段或權限
 
mux.HandleFunc("GET /livez", func(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK)
})

mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 500*time.Millisecond)
	defer cancel()
	if err := db.PingContext(ctx); err != nil {
		http.Error(w, "db not ready", http.StatusServiceUnavailable)
		return
	}
	w.WriteHeader(http.StatusOK)
})
Step-by-step：事故時先看什麼
  1. 先看 SLI：錯誤率、p95/p99 latency、飽和度。
  2. 再用 trace 找慢 span，用 log 找錯誤分類。
  3. CPU 或 memory 異常時才打開 pprof，並確認權限邊界。

Production API Flow：資料流、錯誤流、觀測流

同一個 API 需要同時設計三條路徑：正常資料流、錯誤分類與回應、觀測資料輸出。

Error Flow

錯誤要分類，不只回傳 err

type ErrorKind string

const (
	KindInvalid   ErrorKind = "invalid"
	KindNotFound  ErrorKind = "not_found"
	KindTemporary ErrorKind = "temporary"
)

type AppError struct {
	Kind ErrorKind
	Err  error
}

func (e *AppError) Error() string { return string(e.Kind) + ": " + e.Err.Error() }
func (e *AppError) Unwrap() error { return e.Err }
Step-by-step：HTTP 狀態碼映射
  1. domain 回傳錯誤種類，不直接知道 HTTP。
  2. handler 把 invalid 映射 400、not_found 映射 404。
  3. 暫時性錯誤回 503 並記錄 retryable=true。
Production Checklist

上線前檢查表

所有外部 I/O 都有 context timeout。
DB pool 有上限，並有 readiness check。
錯誤有分類，HTTP response 格式一致。
log 帶 request_id / trace_id。
metrics 有 request count、error count、latency。
pprof 有網路或權限保護。
CI 跑 unit test、race test、basic benchmark。
release note 記錄 migration、rollback 與風險。
Step-by-step：一個 API 的驗收口徑
  1. 功能正確：happy path、validation、not found、DB failure 都測。
  2. 韌性正確：timeout、cancel、retry 邊界清楚。
  3. 觀測正確：錯誤時能從 metric 找到 trace，再從 trace 找到 log。
