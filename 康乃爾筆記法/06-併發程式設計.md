# 06. 併發程式設計 — 康乃爾筆記

> **日期**：2026-05 ｜ **版本基準**：Go 1.22 ｜ **學習目標**：掌握 Goroutine、Channel 及 Context 生態系

---

| 🔑 線索欄（關鍵字 / 問題） | 📝 筆記欄（詳細內容） |
|:--|:--|
| **Goroutine 的特性** | 超輕量級執行緒（起始 2KB），由 Go Runtime Scheduler（M:N 模型）調度<br>啟動成本極低，可以輕易開數萬個 |
| **不要用共享記憶體來通訊** | 💡 **"Do not communicate by sharing memory; instead, share memory by communicating."**<br>優先使用 Channel 傳遞資料，而非 Mutex 鎖變數 |
| **Channel 的種類** | Unbuffered (`make(chan int)`)：同步傳遞，sender 必等 receiver<br>Buffered (`make(chan int, 5)`)：非同步，滿了才會 block |
| **關閉 Channel 的原則** | **必須由 Sender 關閉**，Receiver 關閉或對已關閉的 Channel 傳送會 Panic<br>關閉後 receiver 仍可讀取剩餘資料，讀完後收到零值與 `ok=false` |
| **`select` 的作用** | 讓 goroutine 等待多個 channel 操作<br>若多個 case 同時就緒，會**隨機**選擇一個執行（避免飢餓） |
| **防止 Goroutine Leak** | 啟動 goroutine 前，必須知道它**何時/如何結束**<br>常見 Leak：等待無人發送的 channel、沒有 timeout 的 HTTP 請求 |
| **`sync.WaitGroup` 用途** | 等待一組 goroutine 完成<br>模式：主線程 `wg.Add(1)` → 背景 `defer wg.Done()` → 主線程 `wg.Wait()` |
| **`errgroup` 的優勢** | `WaitGroup` 的升級版（`golang.org/x/sync/errgroup`）<br>解決痛點：**自動收集多個 goroutine 的錯誤**，且任一任務失敗可自動 cancel 其他任務 |
| **`sync.Mutex` 與 RWMutex** | `Mutex`：互斥鎖，保護共享資源<br>`RWMutex`：讀寫鎖，允許多個 `RLock`，但 `Lock` 互斥（適合讀多寫少） |
| **`sync.Once` / `sync.OnceValues`** | 保證某段程式碼在全域只執行一次（如初始化 db 連線）<br>`OnceValues` (Go 1.21+) 可回傳初始化結果與錯誤 |
| **`sync.Map` 的適用場景** | Go 1.9+ 內建的 thread-safe map<br>適用：**讀遠大於寫**（如快取）或 **key 集合獨立且不重疊**<br>日常多讀寫場景，通常用普通 `map` + `RWMutex` 效能更好 |
| **`sync/atomic`** | Lock-free 的底層原子操作（`AddInt64`, `Load`, `Store`）<br>效能極高，適合做計數器、狀態標記 |
| **Context 的核心用途** | 跨 goroutine / 跨 API 傳遞：**Timeout 控制**、**取消信號 (Cancellation)**、**Request Scope 數值 (Trace ID)** |
| **Context Tree 行為** | 樹狀結構。當父節點被 Cancel 或 Timeout 時，**所有子節點都會同時收到 Done 信號** |
| **`context.Cause` (Go 1.20)** | 取消原因追蹤。用 `WithCancelCause` 取消時可附帶 error，用 `Cause(ctx)` 取出精確失敗原因 |
| **`context.WithoutCancel` (Go 1.21)** | 剝離取消信號，但保留 Value。<br>✅ 極適合用於 HTTP 回應後，啟動不受 Timeout 影響的**非同步背景任務** |
| **`context.Background()` vs `TODO()`** | `Background()`：Root context，通常在 `main`、`init` 或最頂層使用<br>`TODO()`：重構時不知道該傳什麼，暫時佔位用 |

---

## 🗒️ 摘要

> Go 的併發模型基於 CSP（Communicating Sequential Processes）。善用 Goroutine 處理非同步，用 Channel 傳遞資料，用 `select` 處理多工。系統穩定性的關鍵在於：絕不留下孤兒 Goroutine，所有外部呼叫都要綁定 Context Timeout。
