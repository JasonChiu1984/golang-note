| 🔑 線索欄（關鍵字 / 問題） | 📝 筆記欄（詳細內容） |
|:--|:--|
| **Goroutine 的特性** | 由 Go runtime 調度的輕量併發工作單位，stack 可成長；起始大小與排程細節不是語言保證。<br>便宜不等於免費，仍應限制工作數與記憶體使用。 |
| **Channel vs Mutex** | 傳遞工作或資料所有權用 channel；保護共享狀態用 mutex。<br>「以通訊分享記憶體」是設計指引，不是禁止使用鎖。 |
| **Channel 的種類** | Unbuffered：傳送必須與接收配對。<br>Buffered：未滿時可送、非空時可收；滿／空時仍會阻塞。 |
| **關閉 Channel 的原則** | 通常由 sender，或確認所有 sender 結束的協調者關閉。<br>不是依「sender／receiver 身分」決定 panic；向已關閉 channel 傳送、重複 close、close nil channel 才會 panic。無需用 close 來釋放記憶體。 |
| **closed / nil channel** | 已關閉 channel 的緩衝資料讀完後，接收立即得到零值與 `ok=false`。<br>nil channel 的 send／receive 永遠阻塞，在 `select` 中等同停用該 case。 |
| **`select` 的作用** | 多個 case 同時就緒時，均勻偽隨機選一個；不保證嚴格公平或取消優先。<br>`default` 會讓等待變成非阻塞，但放在迴圈中可能造成 busy loop。 |
| **防止 Goroutine Leak** | 啟動前決定退出條件與誰負責等待。<br>有 timeout 不代表自動終止 goroutine；阻塞操作與工作函式必須配合取消。 |
| **`sync.WaitGroup`** | 等待一組工作完成，不收集錯誤、不自動取消。<br>舊寫法先 `Add` 再 `go`，工作內 `defer Done()`；第一次使用後不要複製。 |
| **`WaitGroup.Go` (Go 1.25+)** | `wg.Go(func() { ... })` 整合啟動與計數，最後 `wg.Wait()`。<br>不要再寫 `go wg.Go(...)` 或手動 `Done()`；傳入函式不得 panic。 |
| **`errgroup` 的正確語意** | 外部 module：`golang.org/x/sync/errgroup`，不是標準庫 `sync/errgroup`。<br>`Wait()` 等所有已啟動函式返回，回傳**第一個被記錄的非 nil 錯誤**，不是收集全部錯誤，也不是依輸入順序挑錯誤。 |
| **`errgroup.WithContext`** | 第一個任務回傳非 nil error，或第一次 `Wait()` 返回時，取消衍生 context。<br>即使 `Wait()` 成功，衍生 context 也已取消；零值 `errgroup.Group` 沒有這個取消功能。 |
| **取消是合作式的** | 任務要監聽 `ctx.Done()` 或把 ctx 傳給 HTTP／DB。<br>取消不會強殺 goroutine；不配合的任務仍會讓 `Wait()` 卡住。 |
| **`SetLimit` / `TryGo`** | `SetLimit(n)` 限制同時活躍的任務；額滿時 `Go` 本身會阻塞，`TryGo` 則立即回報是否啟動。<br>啟動前設定，活躍期間不可修改；0 禁止新增，負值不限制。限制併發數不等於限制每秒請求數。 |
| **需要所有錯誤？** | 使用每筆任務獨立的 error slot，全部完成後 `errors.Join`（Go 1.20+）。<br>若仍採遇錯取消，未完成的任務可能只回傳 cancellation，無法得到其完整業務結果。 |
| **`sync.Mutex` / `RWMutex`** | 保護共享狀態與跨欄位不變量。`RWMutex` 可讓多個讀者共存，但不一定更快。<br>不要跨越慢速 I/O 持鎖；效能以實際 workload 的 benchmark 決定。 |
| **`sync.Once` / `OnceValues`** | 每個 Once／包裝函式實例執行一次，不是整個程式所有初始化共用一次。<br>`OnceValues`（Go 1.21+）會重用結果與錯誤；失敗後不會自動重試。 |
| **`sync.Map`** | 適合寫入一次後讀很多次，或 goroutine 操作不重疊 key 集合的模式。<br>一般情況先用具型別的 map + 鎖；不能只憑「讀多寫少」推論效能勝負。 |
| **`sync/atomic`** | 優先使用 Go 1.19+ 的 `atomic.Int64`、`Bool`、`Pointer[T]` 等型別。<br>單一操作原子化不會讓多欄位交易自動正確；同一欄位不可混用未同步的一般讀寫。 |
| **container-aware `GOMAXPROCS` (Go 1.25+)** | Linux 會綜合邏輯 CPU、affinity、cgroup CPU quota，並可定期更新。<br>舊 module 的語言版本與 `GODEBUG` 會影響預設；手動設定會停用自動更新，可用 `runtime.SetDefaultGOMAXPROCS()` 恢復。 |
| **Context 的核心用途** | 傳遞 deadline、取消與 request-scoped values；慣例為函式第一參數。<br>取得 cancel 後安排呼叫，避免 timer／父子關係持續占用資源。 |
| **Context Tree** | 父取消會傳遞至一般衍生子 context；不表示所有 goroutine 同時結束。<br>`WithoutCancel` 是刻意切斷取消傳遞的例外。 |
| **`context.Cause` (Go 1.20+)** | 搭配 `WithCancelCause` 保留取消原因；Go 1.21+ 另有 `WithTimeoutCause`／`WithDeadlineCause`。 |
| **`context.WithoutCancel` (Go 1.21+)** | 保留 Value，但移除 deadline、取消與 Cause；`Done()` 為 nil。<br>背景工作仍須加自己的 timeout、關機等待與錯誤處理；重要工作應交給持久化 queue，不能只開裸 goroutine。 |
| **`Background()` / `TODO()`** | `Background()` 是頂層根 context；`TODO()` 是尚未決定 context 來源的占位，不是忽略取消的技巧。 |
| **`testing/synctest` (Go 1.25+)** | 使用 bubble 與虛擬時間測試 timeout／取消；`synctest.Wait()` 等其他 goroutine 結束或進入持續阻塞。<br>它不會虛擬化真實網路 I/O，也不取代 `-race`。 |
| **Go 1.27 併發更新** | `time` 建立的 timer channel 一律同步，移除 `asynctimerchan` 舊模式。<br>`goroutineleak` profile 正式提供，但只能找出部分無法再被喚醒的 goroutine；空報告不等於零 leak。 |

## 1. `errgroup`：失敗通知與完成等待是兩件事

```text
任務 A 回傳 error → 取消 groupCtx → 其他任務觀察取消後返回
                                            ↓
                     所有已啟動任務都返回 → g.Wait() 回傳第一個 error
```

`errgroup` 不會把 panic 轉成 error。父 context 被取消，也不代表 `Wait()` 必然回傳 `context.Canceled`：若所有任務都回傳 nil，`Wait()` 仍可回傳 nil。是否把父取消當成整體失敗，應在 API 契約中明確決定。

以下函式採「父取消視為失敗」的契約，限制 HTTP 併發數，並處理 request 建立錯誤、非 2xx 回應與 body 關閉：

```go
func FetchAll(ctx context.Context, client *http.Client, urls []string, limit int) error {
    if limit <= 0 {
        return fmt.Errorf("limit must be positive")
    }
    if client == nil {
        return fmt.Errorf("client must not be nil")
    }
    g, groupCtx := errgroup.WithContext(ctx)
    g.SetLimit(limit)
    for _, url := range urls { // Go 1.22+：以 := 宣告的 range 變數逐次獨立
        g.Go(func() error {
            if err := groupCtx.Err(); err != nil {
                return err
            }
            req, err := http.NewRequestWithContext(groupCtx, http.MethodGet, url, nil)
            if err != nil {
                return fmt.Errorf("request %q: %w", url, err)
            }
            resp, err := client.Do(req)
            if err != nil {
                return fmt.Errorf("fetch %q: %w", url, err)
            }
            defer resp.Body.Close()
            if resp.StatusCode < 200 || resp.StatusCode >= 300 {
                return fmt.Errorf("fetch %q: HTTP %d", url, resp.StatusCode)
            }
            return nil
        })
    }
    if err := g.Wait(); err != nil {
        return err
    }
    return ctx.Err() // 檢查父 context，不要在此檢查已必然取消的 groupCtx
}
```

完整 import、呼叫方式與測試位於 [`examples/go127`](../examples/go127/README.md)。這個例子只驗證回應狀態，不讀取下載內容；若要重用連線或讀 body，另加有界的讀取策略。呼叫端應提供 timeout，且自訂 `RoundTripper` 也必須配合 context。

> **限制的邊界**：`SetLimit` 不會讓等待名額的 `Go` 呼叫自動因 context 取消而返回。取消後仍可能逐一啟動剩餘 closure，所以要在 closure 開頭檢查 context；若工作清單龐大、需要可取消的派發，改用固定 worker 與有界 queue。也不要在已占滿名額的任務內，阻塞著提交同一 group 的子任務。

## 2. 全部錯誤：自行保存，再合併

```go
func CollectAll(tasks []func() error) error {
    errs := make([]error, len(tasks))
    var wg sync.WaitGroup
    for i, task := range tasks {
        wg.Go(func() { // Go 1.25+
            errs[i] = task()
        })
    }
    wg.Wait()
    return errors.Join(errs...)
}
```

每個 goroutine 只寫自己的 index，且 `Wait` 後才讀取，避免同時 `append` 的資料競爭。`errors.Join` 忽略 nil；全部成功時回傳 nil。這是小批次示範，大量任務還要限制併發。傳入的任務不得 panic，也不要在 `wg.Go` 內再呼叫 `wg.Done()`。

## 3. 版本與實務陷阱

- **Go 1.22 迴圈變數**：新語意適用於以 `:=` 宣告的迴圈變數；`for _, v = range xs` 仍是覆寫既有變數。也要注意 module／檔案採用的語言版本，不能只看已安裝的 compiler。
- **Go 1.25 `GOMAXPROCS`**：quota 不是 CPU request；非整數 quota 會向上取整，通常不會因 quota 單獨降到 2 以下。它限制同時執行 Go 程式碼的容量，不是整個 process 的 OS thread 數量上限。
- **Go 1.27 timer**：不要用 `len(timer.C)`／`cap(timer.C)` 判斷事件是否就緒。需要非阻塞探測時用 `select`；升級時移除依賴舊 timer 緩衝行為的假設。
- **Go 1.27 leak 診斷**：可用 `runtime/pprof` 的 `goroutineleak` profile，或受保護的 `/debug/pprof/goroutineleak`。仍可被全域變數等引用的阻塞同步物件可能漏報，不要把 pprof 直接暴露到公網。
- **測試策略**：以 channel、WaitGroup 或 synctest 建立明確同步，避免用任意 `Sleep` 猜測任務完成。執行 `go test -race`，並測試成功、首錯、父取消與任務確實結束。

## 🗒️ 摘要

> 併發的核心是明確的生命週期、資料所有權與同步。`WaitGroup` 等完成，`errgroup` 傳遞第一個錯誤並可發出取消信號，所有錯誤要自行保存；context 取消只是請求停止，真正結束仍由工作函式負責。
