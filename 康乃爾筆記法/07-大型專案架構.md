# 07. 大型專案架構 — 康乃爾筆記

> **日期**：2026-05 ｜ **版本基準**：Go 1.26.3 ｜ **學習目標**：理解符合現代標準的 Go 專案結構與依賴管理

---

| 🔑 線索欄（關鍵字 / 問題） | 📝 筆記欄（詳細內容） |
|:--|:--|
| **Go 官方推薦的目錄結構？** | 沒有絕對標準，但社群遵循 `golang-standards/project-layout` 慣例：<br>`cmd/` (進入點)、`internal/` (私有邏輯)、`pkg/` (公開工具) |
| **`cmd/` 目錄的職責** | 存放 `main.go`。職責極簡化：讀取設定、初始化依賴（DI）、啟動服務。<br>💡 **不要在 `cmd` 裡面寫業務邏輯** |
| **`internal/` 的強制封裝** | Go 編譯器特性：`internal` 內的 package 只能被其相鄰或上層的 package import。<br>保護業務邏輯不被外部 repo 引用。 |
| **Clean Architecture (洋蔥架構)** | 內層不知道外層。常見分層：<br>`Domain/Entity` (核心模型) → `Repository` (資料介面) → `Usecase` (業務邏輯) → `Delivery` (HTTP/gRPC Handler) |
| **Dependency Injection (DI)** | **依賴反轉**。物件不自己建立依賴，而是從外部（Constructor）傳入。<br>好處：極易替換實作（Mock），方便寫 Unit Test。 |
| **Interface 定義在哪？** | 💡 **"Accept interfaces, return structs."**<br>Interface 應該定義在**需要使用它**的那一層（如 Usecase 定義 Repo interface），而不是實作那層。 |
| **設定檔管理策略** | 遵循 12-Factor App：優先使用**環境變數 (ENV)**。<br>工具：`viper` (支援 yaml/json/env 混用) 或 `kelseyhightower/envconfig` (純 ENV 轉 struct)。 |
| **`Makefile` 的必要性** | 將繁瑣指令標準化。團隊不需記住冗長的 `go build` 參數。<br>常用 target: `make build`, `make test`, `make lint`, `make run` |
| **Error 處理架構設計** | 核心業務層定義 domain error (`var ErrUserNotFound = errors.New(...)`)<br>Delivery 層（Handler）負責將 domain error 對應到 HTTP Status Code (如 404)。 |
| **API 合約是什麼？** | 對外 service 不只看 handler 程式碼，還要固定 method/path、request schema、response schema、status code、error code 與 header。 |
| **錯誤格式怎麼設計？** | 用穩定 envelope：`{"error":{"code":"invalid_input","message":"invalid input"}}`。Client 應依 `error.code` 分支，不依自然語言訊息。 |
| **Request decoder 要守什麼？** | Malformed JSON、unknown field、trailing JSON value 與空白必填欄位都要回 `400 invalid_input`。Decoder 錯誤是 client input problem，不應漂成 `500 internal_error`。 |
| **Request ID 為什麼算合約？** | `X-Request-ID` 讓 response、structured log、trace span 與 metrics route 可以互相對照。若 client 已提供，server 應原樣回傳；未提供才自動產生。 |
| **Panic recovery 要測什麼？** | HTTP handler 邊界要把未預期 panic 轉成 `500` + `{"error":{"code":"internal_error","message":"internal error"}}`，並保留 `X-Request-ID`。 |
| **Readiness 與 liveness 差在哪？** | `/livez` 只回答 process 是否還活著；`/readyz` 回答是否能接新流量。Shutdown 開始後 process 仍活著，但 readiness 應轉為 503 draining。 |
| **Graceful shutdown 順序？** | 先標記 draining，讓 LB 停止導流；再 `http.Server.Shutdown` 等既有 request 完成；最後 close queue 並等待已排入 task drain。 |
| **Contract test 的價值** | 重構 handler 或 service 時，用 `go test ./internal/api -run 'Test.*Contract' -count=1` 固定外部行為，避免破壞前端、CLI 或其他服務。 |

---

## 🗒️ 摘要

> 好的 Go 專案架構不依賴魔法框架，而是依賴**清晰的目錄職責 (`cmd/`, `internal/`)**、**依賴注入 (DI)**、**穩定 API 合約**、**strict request decoding**、**panic recovery 邊界**、**可關聯的觀測性欄位**與**明確的服務生命週期**。維持 Handler、Usecase、Repository 的分層，並用 contract test 守住外部行為，是讓專案易於測試、排障與長期維護的基石。
