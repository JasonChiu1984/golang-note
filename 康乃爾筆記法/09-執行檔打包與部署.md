# 09. 執行檔打包與部署 — 康乃爾筆記

> **日期**：2026-05 ｜ **版本基準**：Go 1.26.3 ｜ **學習目標**：掌握編譯優化、Docker 打包與 CI/CD 實務

---

| 🔑 線索欄（關鍵字 / 問題） | 📝 筆記欄（詳細內容） |
|:--|:--|
| **Go 編譯器的最大優勢** | 單一 binary 部署。若 `CGO_ENABLED=0` 且沒有 C library 依賴，通常可得到純 Go 靜態 binary，可在 `scratch` / distroless image 內運行。 |
| **如何交叉編譯？** | 設定環境變數即可：<br>`GOOS=linux GOARCH=amd64 go build -o app .` |
| **CGO 的影響** | `CGO_ENABLED=1`：允許 Go 呼叫 C 程式碼（如 sqlite3）。常導致 binary 需要系統 C library。<br>✅ 生產環境優先用 `CGO_ENABLED=0`，但仍應用 `ldd` / `otool -L` / container smoke test 確認實際依賴。 |
| **減少 Binary 體積的方法** | `go build -ldflags="-s -w" .`<br>`-s`：移除符號表 (symbol table)<br>`-w`：移除 DWARF 除錯資訊<br>注意：這樣會導致 panic 時的 stack trace 沒有檔名和行號，需權衡。 |
| **編譯時注入版本號** | 透過 `ldflags -X`：<br>`go build -ldflags="-X main.Version=v1.0.0" .`<br>程式內的 `var Version string` 就會被替換為 "v1.0.0"。 |
| **Multi-stage Dockerfile 策略** | 階段 1：使用胖映像檔（如 `golang:1.26-alpine`）下載依賴、編譯 code。<br>階段 2：使用極瘦映像檔（如 `scratch`、distroless 或 `alpine`），**只**把編譯好的 binary 複製過來。<br>結果：Image size 從數百 MB 縮減到數 MB 到數十 MB。 |
| **Go 1.26 release gate** | 同步檢查 `go.mod`、Docker builder image、GitHub Actions `setup-go`、`go tool dist list`、CGO 依賴與容器 smoke test。Go 1.26 需 Go 1.24.6+ bootstrap；Go 1.27 起 macOS runner 需 macOS 13+。 |
| **Dockerfile 依賴快取優化** | 先 `COPY go.mod go.sum` 並 `RUN go mod download`，**然後**才 `COPY . .`。<br>只要 `go.mod` 沒變，Docker 就會快取下載好的依賴，大幅加速 build。 |
| **CI/CD 常見 Pipeline 步驟** | 1. **Lint**: `golangci-lint run`<br>2. **Test**: `go test -race -cover ./...`<br>3. **Build**: `GOOS=linux go build ...`<br>4. **Image**: `docker build ...`<br>5. **Deploy**: Push to Registry / Update K8s |
| **為何 CI 必須跑 `-race`？** | Race detector 會在執行時偵測是否有同時讀寫同一記憶體的狀況。<br>開發機很難測出併發 bug，CI 跑 test 加 `-race` 是最後防線。 |

---

## 🗒️ 摘要

> Go 的部署優勢在於單一 binary 與簡潔 toolchain，但 release 品質取決於版本矩陣是否一致：`go.mod`、Docker builder、CI、CGO 依賴、OS/ARCH 目標與容器 smoke test 必須一起檢查。CI 階段務必加入 `golangci-lint` 與 `go test -race`，確保程式碼品質與併發安全。
